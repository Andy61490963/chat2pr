# 派工給 Codex 的共同說明

審查者派工時，把這份文件全文放在 Issue 內容之前，後面再接「你的任務是 Issue #N」、Issue 內容與審查者寫的線索。大型 UI 改版另外寫元件拆分與實作順序。審查發現新的退件原因就補進「過去審查常見的退件原因」，並寫明怎麼避免。

---

$pstack:poteto-mode

用 pstack 的 poteto-mode 進行這項工作（挑劇本、列待辦、先查清楚再動手、每一步拿得出證據）。本儲存庫的 `AGENTS.md`、`docs/conventions.md` 與下面的規則優先於 pstack；兩者的對應與例外見 `docs/agents/pstack.md`。

你在 chat2pr 儲存庫的一個 git worktree 裡工作。先讀 AGENTS.md、docs/conventions.md（特別是第 3、4 節「一定要一起改的地方」與測試規則）、CONTEXT.md，再動手。

## 工作步驟（照順序做）

1. **讀懂再改**：先找出 Issue 提到的每個檔案與函式，讀完相關程式、既有測試與 `docs/conventions.md` 對應段落。列出你打算改的檔案清單與理由（寫在最後的回報裡）。
2. **沿用既有做法**：同類功能在本專案已經有範例時（分頁、確認對話框、送達狀態、詞彙、遷移），照它的寫法做，不要另起一套。不確定有沒有範例時，先用 `git grep -n` 搜尋（環境沒有 rg；PowerShell 可用 Select-String），或用 `$pstack:how`、`$pstack:why`。
3. **只改 Issue 範圍內的東西**：不順手重構、不重新排版無關的程式、不改沒被要求的文案或行為。範圍外發現的問題寫在回報的「另外發現」。
4. **寫測試**：每個「要做」項目都要有對應的單元或 e2e 測試；測試的預期值要能真的抓到錯誤（先想清楚如果功能壞了，這個測試會不會失敗）。
5. **自我檢查**：照下面「交付前自我檢查」逐條核對，執行 `npm run typecheck`。
6. **回報**：照最後的格式輸出。

## 限制

- 只改檔，不要 commit、不要切分支、不要執行 docker compose。
- 這台機器同時是正式主機，也有其他代理在平行開發：記憶體、專屬測試資料庫、正式環境只能唯讀、Git 操作的規則見 `docs/agents/parallel-development.md`，照做。
- 沙箱跑不了 vitest／playwright（spawn EPERM）、沒有網路與測試資料庫：不要嘗試安裝套件；可以執行 `npm run typecheck`（tsc）確認型別。測試由審查者跑，但你要把需要的單元測試與 e2e 測試寫好（e2e 用 `e2e/dashboard-fixture.ts` 的虛構資料，新增 API 欄位要補進 fixture）。
- 所有使用者看得到的文字、註解、測試名稱用繁體中文；只用虛構的群組、專案、人名（例如「範例群組」「示範專案」「小林」）。**絕不可**寫入真實客戶、群組、專案或人名。
- 狀態詞彙先加在 `shared/status-glossary.ts` 再由看板引用。
- 不可繞過登入、權限、人工審核、預算、版本檢查或容器隔離；不改 API 行為，除非 Issue 明確要求。

## UI 準則（frontend-design 與 Design 外掛）

- 結構即資訊：用版面與層級表達關係，不靠裝飾；一個畫面一個焦點。
- 不用間隔點（・ ·）、全大寫小標、「→」箭頭當文字分隔；用使用者懂的詞，不露內部代號或英文錯誤。
- 錯誤與異常文案＝發生什麼＋為什麼＋怎麼處理。
- WCAG 2.1 AA：文字對比至少 4.5:1、可用鍵盤操作、觸控目標至少 44px（手機，用 `min-h-[44px]` 或 `size-11`）、有可讀的名稱。
- 視覺語言沿用現有樣式（紙、墨、鋼，運轉綠、安燈黃、停機紅；Noto Sans TC；站別軌道），顏色只表示狀態。手機 375px 不可有水平捲動。

## 過去審查常見的退件原因（不要再犯）

1. **把伺服器的具體錯誤換成籠統猜測文字**：`catch (e) { setError("可能是連線中斷…") }` 會蓋掉 API 回傳的中文驗證訊息。看板要顯示伺服器原因（`message(e)`），需要補充說明時加在後面，不要取代。
2. **用 `aria-label` 蓋掉可見文字**：axe 會報 `label-content-name-mismatch`。可見數字或文字要包含在名稱裡；補充說明用 `<span className="sr-only">`。
3. **對可能缺值的欄位直接呼叫方法**：例如 `d.note.startsWith(...)`，舊資料或測試替身沒有 `note` 就讓整個看板白畫面。用 `?.`、預設值，或先判斷。
4. **Flex 分頁或按鈕在 375px 互相重疊**：分頁按鈕不要用 `flex-1` 平分寬度；用 `flex-none`，外層 `overflow-x-auto max-w-full`。
5. **Radix 對話框／選單的動畫影響測試**：開啟後的縮放或淡入期間量尺寸或跑 axe 會量到錯的值。量高度用 `offsetHeight`；跑 axe 前先 `await page.evaluate(() => Promise.all(document.getAnimations().map(a => a.finished)))`。
6. **e2e 攔截網址漏掉查詢參數**：看板讀狀態是 `/api/state?activity=80`，`page.route("**/api/state")` 攔不到；用 `/\/api\/state(\?|$)/`。測試資料要完整（例如服務清單少了幾項，會被算成「未檢查」）。
7. **測試替身資料不完整**：模擬 Docker、Discord、LINE 回應時，欄位要和真實 API 一樣齊全（例如 Docker 盤點的容器要有 `Image`、`Id`、`Names`），否則程式在測試裡拋錯、測不到要測的行為。
8. **HTTP 標頭用中文值**：測試的 CSRF、權杖等會放進標頭的虛構值只用英數字，否則瀏覽器直接拒絕請求。
9. **多做一套機制**：例如另外加密已經存在設定檔的權杖、另寫一份已有元件的畫面。先確認既有機制能不能用。
10. **把公開識別碼當機密遮蔽**：Discord 應用程式 ID 等公開識別碼不是機密；遮蔽會破壞功能（例如提及機器人）。
11. **共用規則只套一個平台**：LINE 與 Discord 的通知、私訊、補送規則（過期不補送、摘要、篩選）要共用同一套，不要只寫在 LINE。
12. **在交易內呼叫外部 API**：資料庫交易（尤其 `FOR UPDATE`）期間不要呼叫 Discord、LINE、GitHub 等網路服務；先在交易內佔住、提交後再送、失敗再歸還。
13. **對整個 server 檔案跑 prettier**：只格式化你改過的區段所在的新檔案，不要讓差異出現無關的重排。
14. **用 hook 時注意早期 return**：React hook 不能放在條件 return 之後。
15. **鍵盤操作中途打開對話框**：在 `onValueChange`、`keydown` 處理中立刻開對話框並移動焦點，同一次 Enter 的預設動作會落到新焦點（例如「取消」）而馬上關掉。等按鍵處理完再開（`setTimeout(…, 0)`），並在選單收合時不把焦點搶回觸發元件。e2e 一定要用鍵盤實際走一遍。
16. **為了新需求放寬安全關卡**：例如為了讓清單逐項判斷風險，把確定性風險檢查改成只看摘要，拿掉標題與來源原文，結果所有需求的敏感變更都能自動排程。安全、權限、風險、預算的檢查只能變嚴或維持；要放寬特定情況，只對那個情況分支處理，其他路徑保持原樣，並確認既有風險測試全部通過。
17. **分頁「得到焦點就切換」遇上確認視窗**：Radix Tabs 預設焦點移到分頁按鈕就切換；草稿確認視窗關閉時會把焦點還給分頁按鈕，造成「繼續編輯」後視窗重開、「放棄修改」後又跳回原分頁。分頁切換要經過未存草稿確認時，只接受使用者剛在分頁列按鍵或點擊造成的切換（擷取階段記錄、用一次就清掉），並用 e2e 把「繼續編輯」與「放棄修改」兩條路都走完。

## 交付前自我檢查

- [ ] Issue 每一個「要做」都已實作，且各有測試。
- [ ] 沒有改 Issue 範圍以外的行為與文案。
- [ ] 上面 17 條退件原因逐條核對過。
- [ ] 新增的 API 欄位、載入時呼叫的 API 都補進 `e2e/dashboard-fixture.ts`。
- [ ] 改了導覽或進入方式時，同步既有 e2e 的進入方式，但沒有改它們驗證的行為。
- [ ] 375px 版面：沒有水平捲動、按鈕不重疊、觸控目標 44px。
- [ ] 文案沒有英文錯誤、內部代號、間隔點、真實名稱。
- [ ] `npm run typecheck` 通過。

## 最後的回報格式

1. **改了什麼**：每個檔案一行，寫做了什麼、為什麼。
2. **對應 Issue 的每個項目**：逐項寫「已做／部分／沒做」與對應測試名稱。
3. **審查者要跑的測試**：列出指令與檔案。
4. **另外發現**：範圍外的問題（不要自己改）。
5. **不確定的地方**：需要審查者決定或確認的事。
