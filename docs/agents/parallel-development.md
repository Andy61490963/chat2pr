# 多個代理平行開發

這台開發機同時是正式主機。多個代理（Claude Code 子代理、Codex）可以各在一個 worktree 平行開發 chat2pr，但要守下面的規則，測試結果才可信、正式服務不受影響。派工時直接指向這份文件。

每條規則都附原因；原因不再成立時才可以改規則。

## 1. 記憶體

| 規則                                                                                                                                                                                                    | 原因                                                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 跑重的指令（完整 `npx vitest run`、playwright、真實 Docker 測試）前先查可用記憶體：`powershell -NoProfile -Command "[math]::Round((Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory/1MB,1)"`。 | 可用記憶體低於 2 GB 時，正式派工會被暫停，真實使用者的需求卡在排隊。                              |
| 低於 6 GB 就等 1–2 分鐘再查，不要硬跑。                                                                                                                                                                 | 多個代理同時跑完整測試曾把可用記憶體壓到 0.4 GB（2026-11-23）。留 4 GB 餘裕給其他代理與正式服務。 |
| 完整 vitest 與 playwright 不要同時跑；playwright 一律加 `--workers=2`。                                                                                                                                 | 兩者各會開多個 node 程序，加起來的尖峰最容易把記憶體壓到底。                                      |
| 開發時只跑受影響的測試檔；完整測試只在交付前跑一次。                                                                                                                                                    | 完整測試佔用最多記憶體與時間，迭代時跑它幫不上忙。                                                |
| 測試結束後確認沒有自己 worktree 殘留的 vite／node 程序（`Get-CimInstance Win32_Process -Filter "Name='node.exe'"`，看 CommandLine 的路徑）。                                                            | 被中斷的測試會留下常駐程序，持續佔用記憶體，別人查到的可用記憶體就不準。                          |

## 2. 測試資料庫與連接埠

| 規則                                                                                                                                                                                                          | 原因                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 每個 worktree 用自己的資料庫，名稱以 `_test` 結尾（例如 `agentflow_e_test`），建在已啟動的 `line-agentflow-db-test-1` 裡：`docker exec line-agentflow-db-test-1 createdb -U agentflowtest agentflow_e_test`。 | 測試每次都會遷移並清空資料表；共用的 `agentflow_test` 被兩個分支同時清空會出現 `deadlock detected`，各分支的遷移也會疊加，造成假失敗。 |
| 跑測試前設定 `TEST_DATABASE_URL`：把 `tests/helpers.ts` 預設網址的 `agentflow_test` 換成自己的名稱。不要用預設的 `agentflow_test`。                                                                           | 沒設定就落到共用資料庫。`tests/helpers.ts` 只檢查名稱以 `_test` 結尾，擋不住兩個人用同一個。                                           |
| e2e 以 `E2E_PORT=<自己的埠號>` 執行。                                                                                                                                                                         | `playwright.config.ts` 預設 4521；兩個 worktree 都用預設時，後啟動的會連到別人的開發伺服器，測到別的分支的程式。                       |
| 真實 Docker 測試建立的容器、網路、資料卷用每次執行唯一的 instance 名稱（`verify-<測試>-<隨機後綴>`），清理只依自己的 instance 標籤。                                                                          | 固定名稱（例如 `verify-i19-checks`）在兩個 worktree 同時跑時會撞名，其中一份整檔失敗；依標籤清理也會刪掉另一份還在用的容器（#258）。   |

## 3. 正式環境只能唯讀

| 規則                                                                                                                     | 原因                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| 查正式資料只用部署目錄的 `docker compose exec -T db psql -U agentflow -d agentflow -tA -c "SELECT ..."`，只准 `SELECT`。 | 正式資料庫的寫入屬於使用者的決定，見 `AGENTS.md`。                                                        |
| 不在部署目錄改檔、切分支、執行 `docker compose up` 或 `npm run deploy`；不讀 `.env`、`.local/`、`.codex-service/`。      | 監督程序每 30 秒在部署目錄執行 `docker compose up -d`，改檔或切分支會重建正式容器；那三處放的是正式機密。 |
| 測試只動自己建立、名稱帶測試前綴（`verify-`、`agentflow-verify-`）的容器與資料卷，不碰 `line-agentflow-*`。              | `line-agentflow-*` 是正式容器；刪掉或重建會中斷正式服務。                                                 |
| 真實名稱（專案、群組、人名）只留在腦中，不寫進檔案、commit、Issue、PR 或回報；用「示範專案」「群組 A」代稱。             | 正式資料庫裡有真實客戶資訊，寫進 Git 就收不回來。                                                         |

## 4. Git 與 worktree

| 規則                                                                                                                              | 原因                                                                                                                                                                                             |
| --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 要把自己的 commit 壓成一個時，用 `git reset --soft "$(git merge-base HEAD origin/main)"`，不要用 `git reset --soft origin/main`。 | 所有 worktree 共用同一個 `origin/main` 參照，別人 `git fetch` 就會把它往前移。`reset --soft origin/main` 把基底換成較新的 main，暫存區卻還是你舊的檔案，新 commit 等於把別人剛合併的修改改回去。 |
| 只在自己的 worktree 與分支工作，不切分支、不動其他 worktree。                                                                     | 其他 worktree 可能有別的代理還沒 commit 的修改。                                                                                                                                                 |
| 不要在 worktree 執行 `npm install`；缺套件就回報。                                                                                | worktree 的 `node_modules` 是連到共用套件的連結，`npm install` 會把連結換成實體資料夾，佔空間又和其他 worktree 的版本分岔。                                                                      |
| 移除 worktree 前先 `cmd /c rmdir <worktree>\node_modules` 拆掉連結。                                                              | 直接刪 worktree 會連共用套件一起刪，其他 worktree 全部壞掉。                                                                                                                                     |

## 5. 測試結果要可信

| 規則                                                                                                                                 | 原因                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| 完整 `npx vitest run` 在開發機上不應有「本來就失敗」的項目。需要本機沒有的工具或映像的測試，偵測到缺少時略過並印出原因，不要算失敗。 | 每次都要解釋「這一項本來就失敗」，真的壞掉時反而看不出來。                                                            |
| 略過的原因直接寫到 `process.stderr`（並用 `ctx.skip(原因)`），不要只用 `console.warn`。                                              | vitest 預設報告器不顯示通過或略過項目的 console 輸出，原因會被吞掉；`ctx.skip` 的原因只在 `--reporter=verbose` 顯示。 |
| 目前已知的略過：PDF 文字層測試在沒有 poppler（`pdfinfo`、`pdftotext`）的機器上略過；真實 Docker 測試找不到對應映像時略過。           | Git for Windows 只附 xpdf 版 `pdftotext`、沒有 `pdfinfo`。正式映像（`Dockerfile`）有安裝 poppler，不受影響。          |
