# 專案慣例與注意事項

UI 改動先讀 [`src/AGENTS.md`](../src/AGENTS.md)，以便重用已有元件，讓頁面的尺寸與狀態色跟隨同一組代幣。

新增任務、專案或群組的狀態時，請先在 `shared/status-glossary.ts` 加入顯示名稱，再由看板引用。

這份文件收集「不寫下來就容易踩到」的規則：哪些事一定要一起改、哪些指令不能在哪裡執行、哪些錯誤其實是正常現象。人和 AI 代理在這個儲存庫工作前都應該讀過一次；發現新的潛規則就補在這裡，不要只留在對話或個人筆記。

每條規則都附上原因。原因不再成立時，連同規則一起刪掉。

## 1. 語言與協作

| 規則                                                                                                                                                                                                           | 原因                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文件、使用者介面、Issue、PR、commit 訊息一律使用繁體中文。                                                                                                                                                     | 使用者與維護者都以繁體中文溝通；混用語言會讓看板與通知不一致。                                                                                                                                                                                                                                          |
| commit 與 PR 標題用 [Conventional Commits](https://www.conventionalcommits.org/zh-hant/) 格式：`類型: 說明`。類型用英文小寫，說明用繁體中文，例如 `fix: 查詢的機密判斷只看使用者原文`。                        | 一眼看出每次變更的性質，也方便產生版本說明。                                                                                                                                                                                                                                                            |

| AI 開發以 pstack 為基準（`docs/agents/pstack.md`）；跨檔案、需要設計或原因不明的工作從 `poteto-mode` 開始。pstack 與本文件衝突時以本文件為準，並把衝突補進 `docs/agents/pstack.md` 的「本專案的例外」。        | 讓 Claude Code 與 Codex 用同一套方法：先查清楚、每一步有證據、同一個錯改結構擋住；但正式環境、部署目錄、測試資料庫的限制是本專案特有的，通用 skill 不會知道。                                                                                                                                           |

## 2. 兩個目錄：部署目錄與開發目錄

同一台主機上至少有兩份程式碼：

- **部署目錄**：有 `.local/secrets.json` 的那一份。監督程序每 30 秒用這裡的 `compose.yaml` 執行 `docker compose up -d`。
- **開發目錄**：另外 `git clone` 或 `git worktree add ..\chat2pr-dev -b 分支 origin/main` 建立。

| 規則                                                                                                         | 原因                                                                                          |
| ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 部署目錄只用 `npm run deploy` 更新，不在裡面切分支、改檔或 commit。                                          | 在這裡切到改過 `compose.yaml` 的分支，正式容器會在 30 秒內被重建。                            |
| 部署目錄固定停在分離 HEAD 的 `origin/main`，不需要本機 `main` 分支。                                         | 本機 `main` 可能被其他工作目錄佔用；`npm run deploy` 一律 `git switch --detach origin/main`。 |
| 開發目錄不要執行 `docker compose up`、`down`、`build app`。                                                  | Compose 專案名稱固定為 `line-agentflow`，從開發目錄執行會動到正式容器。                       |
| 開發目錄可以 `docker build -f worker/Dockerfile -t <臨時標籤> .`，但不要覆寫 `line-agentflow-worker:local`。 | `:local` 是正式執行器使用的工作映像；開發分支的映像蓋上去等於未經部署就上線。                 |
| `npm run deploy` 在開發目錄會拒絕執行。                                                                      | 開發目錄沒有 `.local/secrets.json`，這是刻意的保護。                                          |

## 3. 一定要一起改的地方

訂閱轉送層的 502 只代表轉送失敗；請看該階段執行事件裡訂閱代理記錄的固定類別與上游 HTTP 狀態碼（若有），不要從轉送層的 502 推測上游也回了 502。

調整訂閱重試時，一起核對 `shared/upstream-failure.ts` 的可重試類別、訂閱代理的階段連敗上限與 `worker/provider.mjs` 的 CLI 重試設定。代理保留授權且 CLI 願意重送，工作才有機會恢復。只有下一次請求實際送往上游時才記重試事件，避免把最後一次失敗也算成重試。

修改任務結束稽核的種類或文字格式時，同步更新 `server/task-end.ts` 的解析與 `tests/task-end.test.ts` 的樣本。若調整結束稽核的種類，也要同步更新 `server/schema.sql` 的 `audit_task_ending` 索引條件。看板依同一規則取得最新結束紀錄，才能讓任務列表與詳情顯示一致，又避免逐張查詢。

修改收集結果（`worker/trusted-changes.mjs` 的 `files`：path、base64 內容、mode）或 `runs.result` 的寫法時，同步核對 `server/execution.ts` 的接續點 `candidate`（`resumableCandidate`、`candidateKey`）與 `server/containers.ts` 的 `applyCandidate`，並跑 `tests/execution.test.ts` 的接續案例與 `tests/containers.test.ts` 的寫回案例。中斷後的下一次執行靠這份紀錄把修改寫回新副本、從測試與獨立審查接續（#241）；`runs.result` 存成 jsonb 後欄位順序會變，比對候選內容要逐欄比，不能直接比 JSON 字串。發布時 `runs.result` 會換成 PR 結果，查接續點時要把有 `prUrl`／`answer` 的執行也算成「最近一次」，否則會撿回更早、已被取代的候選。新增會判定候選不能用的檢查（驗證、複驗、機密、寫回）時，丟錯前先呼叫 `settle()`，再做暫停檢查或切換階段；否則剛好暫停或逾時，下一次重試會再接續同一份註定失敗的修改，重複消耗每日次數與審查額度。派工的基底也由這份接續點決定（#261）：有可接續的候選就用它的 `baseSha`，否則用目標分支（追加修改則是 PR）目前的 head；不要另加旗標或在別處沿用舊的 `tasks.base_sha`，否則修好目標分支後重試會一直卡在舊基底的驗證失敗。

單次執行逾時、修改已保留時自動接續一次（#256）的計數以 `audit` 的 `auto_resume` 為準（detail 含「需求版本 N，」），由 `server/execution.ts` 的 `claimAutoResume` 在鎖住任務列的同一交易內計數、放回排隊、寫稽核與排入群組進度 `group_resumed`。改 `auto_resume` 的稽核文字時要保留「需求版本 N，」，否則計數歸零，同一版本會接續兩次。接續前由 `resumeShortfall` 核對今日執行次數（訂閱模式）或今日預算（API 模式，不算這次執行自己的預留）；不夠就不接續，照 #246 的說明失敗，並在建議與群組訊息寫出額度原因。原因：重新排隊後才在派工時被額度擋下，任務會停在「等待額度」到隔天，管理者以為已經在接續；先判斷才能如實說明。新增群組通知種類 `group_resumed` 時已同步 `retrievable` 與 `staleNotification`，只在這個需求版本的接續還沒結束時可取回（鍵 `group:resumed:<任務>:<版本>`）。群組失敗說明 `group_failed` 的鍵是 `group:failed:<執行>`，每次失敗各一則，同任務有較新的一則時舊的過期。原因：鍵若只含任務，重試或接續後再失敗會撞鍵不寫入，群組最後一則停在「系統會自動接續」。舊版鍵 `group:failed:<任務>` 的列不遷移，與新鍵並存時一樣依建立時間只送最新的。被接續的那次執行 `runs.outcome` 記成 `auto_resumed`，執行紀錄與鈴鐺共用 `notificationLabels.autoResumed`。

修改衍生映像的鍵或標籤時，同步更新 `tests/derived-image.test.ts` 與 `tests/derived-image-cleanup.test.ts` 的樣本。重建後的清理用套件識別與基底 ID 標籤比對，缺少任一標籤的映像交給每日規則。這樣才能分辨同套件的舊基底，並保留較早版本建立、無法確認套件識別的映像。

## 4. 測試

瀏覽器驗收（`npm run test:e2e`）跑在 Vite 開發伺服器上，沒有正式伺服器的安全標頭（CSP、`frame-ancestors`、X-Frame-Options）。牽涉這些標頭的行為（例如同源 iframe 嵌入）要另外用 `buildApp` 的整合測試檢查；系統頁的架構動畫就曾在 e2e 通過、正式環境卻被 `frame-ancestors 'none'` 擋下。

啟動真實排程器的測試替身須依執行器端點回傳對應格式。即使只驗證判讀或派工，排程也會同步定期檢查環境；`checks/environments/sync` 沒有清除項目時仍須回傳 `{ removed: [] }`，否則測試可能通過卻在背景留下同步錯誤。

- 看板頁面若新增載入時會呼叫的 API，請同步更新 `e2e/dashboard-fixture.ts` 的虛構回應。瀏覽器驗收會攔截 API，缺少回應時回傳 404，可能讓測試只驗到錯誤畫面。
- 新增看板頁面或改變預設頁籤時，請同步調整 `e2e/accessibility.spec.ts` 的頁面與載入條件。掃描要等到實際內容出現，才能抓到欄位缺少標籤、頁籤指錯面板或文字對比不足。
- 使用 Radix 分頁的 `forceMount` 保留設定草稿時，未選取的面板要加 `hidden`。`forceMount` 會讓面板維持掛載，必須另外隱藏，才能讓鍵盤與讀屏只讀到目前分頁的內容。

## 5. 機密與權限

- 資料庫與 SSH 連線的白話整理可能含有憑證。訂閱模式呼叫執行器 `/ai` 時帶上 `sensitive`，讓容器透過即時附接回傳輸出並停用日誌驅動程式，避免模型輸出被寫入容器日誌。
- 更新工作映像的 `iputils-ping` 時，保留安裝後移除 `ping` 檔案能力與 setuid 的步驟。Debian 12 套件可能設定這些屬性，工作容器已移除所有能力，應透過 Docker 的 `ping_group_range` 允許的 ICMP datagram socket 執行 `ping`。
- 看板鈴鐺與活動清單在伺服器依登入角色取資料。修改通知內容時，一起核對管理者私訊、群組原文的保存期限，以及活動清單與總數的可見範圍，避免同一段管理訊息改從另一個欄位顯示。
- 新增會等待使用者處理的通知種類時，在 `server/dashboard-alerts.ts` 一起定義何時待處理、何時已處理，並核對通知的需求版本或問題編號。通知歷史會保留，版本更新、補問回答或任務結束後才不會繼續累加未讀。
- 測試輸出、指令輸出、錯誤訊息與 AI 產出送到看板、群組、通知、稽核、執行紀錄或 AI 提示前，一律經過 `redact`（`server/policy.ts`）或 `safeDetail`（`server/observation.ts`）。新的帳密格式只加在 `shared/credentials.ts` 的 `maskCredentials`，並在 `tests/secret-masking.test.ts` 補「含機密→不含密碼」與「不含機密→不變」兩種案例。要截斷輸出時先遮蔽再截斷。原因：測試失敗訊息常帶 `postgres://帳號:密碼@主機` 或 `Password=…` 連線字串（#252）；先截斷會切掉網址開頭，剩下的半段密碼就認不出來。遮蔽規則以帳密為限，公開識別碼（例如 Discord 應用程式 ID）不遮。
- `runs.result` 新增可能引述需求原文的欄位時，同步加進 `server/schema.sql` 的 `erase_candidate_quotes`，撤回與到期時才會清掉；觸發器 `erase_run_content` 與 `server/maintenance.ts` 的每日清理共用它。原因：#246 的候選修改說明與審查意見原本會留到 30 天清理。
- 呼叫 LINE API 時，網路例外只傳遞固定的連線說明。需要辨識額度或限流時，在請求邊界分類 HTTP 回應，避免將權杖、標頭或未經處理的錯誤內容帶進健康狀態與稽核。

## 6. 部署與維運時的「正常現象」

個人保留比例的儲存與額度檢查必須共用 `lockSubscriptionGate`，並在儲存比例的同一筆交易清除舊的額度判定。這樣進行中的額度查詢才不會在設定更新後寫回舊比例的結果。

部署帶回主機程序的潛規則（`scripts/deploy.mjs`、`scripts/lib/host-start.mjs`）：

- **排程工作「存在」不等於啟動得了**：已停用時 `Start-ScheduledTask` 會失敗，舊版部署只看存在就當成功，停掉主機程序後帶不回來，正式環境停到有人手動啟動（#250）。現在停之前先查狀態，啟動後要看到 `start-windows.mjs` 程序才算數，否則直接在背景啟動；兩條路都走到也只會有一個監督程序（`.local/supervisor.pid`）。
- **部署不自動重新啟用排程工作**：停用可能是有人刻意暫停服務（部署手冊「停止與移除」），只提醒、不替人改回來。

服務異常通知的潛規則（`server/health.ts`、`server/capacity.ts`、`server/tunnel-provider.ts`）：

- **通道狀態檔過期時不可沿用檔內的說明**：外部通道程序停住時，檔案最後寫的是「已連線」，沿用會變成「異常：已連線」。過期一律寫「通道狀態檔已 N 分鐘沒有更新」（`tunnelReading`）。
- **記憶體是否在暫停中看 `reading_ok`，不看 `notified_ok`**：通知基準要連續兩次讀數才改，用它判斷時，回升後的第一次正常讀數會被下一輪拉回暫停並重新起算穩定期。只有沒有 `reading_ok` 的舊列才退回看 `ok`／`notified_ok`。
- **有通知門檻的項目（`noticeDelay`）首次建立時通知基準一律記為正常**：否則第一次讀數就是異常時永遠不發異常通知，恢復時卻會發一則沒頭沒尾的「已恢復」。

推播額度相關的潛規則（`server/line-quota.ts`、`shared/line-quota.ts`）：

- **額度用完不能計入 `attempts`**：每月上限要到下個月才恢復，算進失敗次數的話，每則通知約一分鐘內就撞滿 3 次被永久放棄。只有 429 加上 `monthly limit` 訊息才算額度用完；一般 429 是短時間限流，照舊累加。
- **恢復後不得補送過時的群組訊息**：解除暫停與按「重送」前都要先跑 `expireStaleNotifications`。群組推播依人數計費，幾週前的排隊說明、舊版補問一次推出去，新月份的額度當天就會用完，成員也會收到已經不對的內容。
- **額度狀態不可併進 `'line'` 檢查，也不放進 `server/health.ts` 的 critical 清單**：解除全域暫停要求 `'line'` 一天內正常，額度用完時收訊與「收到」其實照常，併進去會讓管理者連暫停都解不開；critical 會再排一則「服務異常」私訊，這時根本送不出去。
- **解除暫停只看 LINE 額度 API 的回報**，不用日期推算：LINE 換月的時區與方案升級都不在我們手上。額度 API 回應看不懂時當成「讀不到」，不能當成上限 0，否則會把推播整個停掉。
- **群組推播依人數計費，額度判斷要用剩餘則數對群組人數，不能只看 `used<limit`**：剩 5 則時推給 8 人的群組，LINE 一樣回 429 monthly limit。只看 `used<limit` 會每小時解除一次、又撞一次，排在後面的私訊也一起卡住。所以：
  - 解除暫停的條件仍是「剩 1 則以上」（私訊可送）；群組能不能送由 `flushNotifications` 逐則用 `quotaRemaining`（`line_quota` 說明裡的用量）對 `pushCost(groups.member_count)` 判斷，不夠就略過那個群組（不加 `attempts`，`last_error` 寫 `quotaShortForGroup`）。
  - 群組先送，當輪累加的用量要寫回後才能判斷私訊保留門檻；測試私訊也須經過同一門檻。推播與額度同步共用鎖，避免同時使用同一份剩餘額度。
- 尚無 LINE 用量紀錄時，私訊摘要與測試通知照常嘗試推播，由 LINE 回應判定是否已達月上限。用量未知時先暫停會讓首次或尚未完成額度同步的通知無法送出，也進不了既有的重試流程。
  - 私訊摘要在呼叫 LINE 前保存批次識別碼，重試沿用相同的 LINE 重試鍵。用同一個鍵重送已收下的摘要時，LINE 回 409，系統仍視為送達，避免網路逾時造成重複推播。
  - 私訊摘要的 10 分鐘窗口從成功送出開始算。過期或留在看板的通知也可能有 `sent_at`，只有帶批次識別碼且沒有 `last_error` 的已送通知才能開啟窗口，避免略過的通知延後待確認私訊。
  - 服務異常的私訊判斷要核對同一次中斷的開始時間，且在滿 15 分鐘後還要有異常讀數，避免把新一輪異常或已恢復的短暫中斷當作長時間中斷。看板沿用原本的異常與恢復通知時機。
  - 每送一則就在本地把用量加上人數（未知時 1）並寫回說明，不必每則都查額度 API；連線檢查每小時再以 LINE 的回報校正。
  - 群組撞到 429 monthly limit 時先查額度 API：還剩 1 則以上只是不夠這個群組，本輪略過群組、私訊照送，並把這個群組記成「至少剩餘＋1 人」（`markGroupTooLarge`），24 小時內不再對它撞 429；剩 0 則、查不到或私訊也撞到才整個封鎖。
  - 封鎖時要保留用量（`markQuotaExhausted` 沒給用量就沿用原說明解析出的），看板才顯示得出「本月已用 X／上限 Y」。
  - 因人數不夠而略過的群組通知，續送前要先跑 `expireQuotaHeld`（`last_error` 以 `quotaShortPrefix` 開頭、這輪不再略過的群組，過時的標成已過期）。原因：這種略過不會進入 `line_quota` 封鎖，`syncLineQuota` 解除封鎖時的 `expireStaleNotifications` 管不到；大群組可能被略過幾週，換月額度一恢復就會把舊說明推給整個群組。還在略過的群組不動，成員仍可用 `/進度` 取回 7 天內的回覆。
- **群組人數 API（`/v2/bot/group/{id}/members/count`、聊天室用 `/v2/bot/room/{id}/members/count`）不計推播額度，但仍要快取 24 小時**：通知排程每 20 秒跑一輪，每輪都查會無謂地打 LINE；只有剩餘額度已知且有上限時才需要人數。

## 7. AI 判讀與查詢的規則

這些規則改過不只一次，修改前先讀對應的測試（`tests/query-routing.test.ts`、`tests/project-confirmation.test.ts`）。

- **修改任務一律人工確認**，不論風險或專案是否明確。
- **拒絕原因只影響自動辨識**（`server/triage.ts` 的 `recentRejections`，`tests/triage-rejections.test.ts`）：同群組 30 天內以「不是給 AI 的工作」「需求還沒定案」拒絕的需求（最多 10 筆）只在本批有自動辨識訊息時放進判讀上下文，相似訊息歸為 `noTaskReason=similar_rejected` 並留下略過紀錄。原因：管理者曾連續拒絕三十多筆沒有原因的任務，系統學不到；但 `/任務` 與提及機器人是成員明確要求，不能因為過去的拒絕被略過。原因代碼的顯示文字在 `shared/status-glossary.ts` 的 `endReasonLabels`，改代碼要同步既有 `tasks.end_reason` 資料。
- **未定案的討論等新訊息或到期再判讀**：`noTaskReason=undecided_discussion` 的訊息在群組有符合觸發方式的新訊息時一起判讀，否則從各則訊息的收訊時間算滿 15 分鐘才做最後一次判讀，仍未定案就略過。普通未說完片段維持約五分鐘重判，單靠片段重試不會帶回未到期的討論。活動紀錄用固定文字說明等候或略過的原因，避免保存原文或模型改寫。
- **判讀補問與假設**：`question` 只能是一個問題（常見答案最多三個），`assumptions` 保存可修正且有依據的預設；系統把假設統一附加在摘要中，沿用 `task_versions` 保存版本。查詢一律移除開發方案；修改只有產品方向不同時提供方案、唯一推薦與理由。未回答任務的單一假設修改會產生新版本、保留未解問題並作廢舊核准；已回答查詢改為沿用對話串建立追問，保留原回答。方案與問題的跨欄位不符由 `clarifyDecision()` 修正並留下「已調整 AI 輸出」稽核，不讓可修正的輸出造成整批判讀失敗。單一方案改為確認問題，不擅自採用為假設。整份需求編輯以使用者摘要為準並清除舊結構標記，避免兩份內容不一致。
- **備份第 4 版**包含任務的問題與假設；還原第 1～3 版時新欄位使用預設值並提示核對原摘要。
- **備份第 5 版**包含待挑選清單；還原第 1～4 版時清單為空。備份不含聊天原文，從還原的清單建立任務時會提示核對無法查看的來源。
- **查詢可以自動執行**的條件：本次訊息明確指名專案（完整儲存庫、專案名稱，或在已登記專案中唯一且至少 6 個字的儲存庫名稱／去括號名稱），或有唯一的檔案證據；並且沒有要求交出機密實際值。
- **索引超限時可預選修改專案**：群組只有一個可派工專案、該專案的程式索引超限，而且新訊息的具體需求與專案說明相符且無衝突時，可將目標標為明確並預選，交給管理者確認。判讀必須引用需求原文及專案說明，伺服器核對引用與索引狀態後只保存固定理由。查詢沿用明確指名或唯一檔案證據的條件。
- **修改風險逐項比對**：關鍵字只比對各決策自己的摘要與驗收，同一則會議紀錄中其他項目的關鍵字不會觸發本項提醒。模型的風險提示也逐項填寫，清單在挑選前顯示各項自己的提醒。
- **機密判斷只看使用者原文**，不看 AI 改寫的摘要與驗收（AI 常寫「列出…」「提供…」，會造成誤判）。AI 列出的風險只當提醒，除非寫明「要求揭露／輸出」。
- **跨專案查詢**：指名的專案都必須綁定本群組；其他專案的原始碼唯讀放在 `/agentflow/env/projects/<儲存庫名稱>`。人工指定的參考專案在更換主要專案的目標分支時仍保留，因為參考專案各自使用設定分支。
- **未綁定的專案建議**：只保存引用訊息的識別碼，顯示原文時沿用撤回與保存期限。建議比對只在伺服器執行，避免未綁定專案的程式內容進入 AI 提示或通知。一鍵綁定與指定在同一筆交易完成，由既有群組綁定觸發器更新版本與通知，維持人工確認。
- 查詢報告的來源版本存在該次執行的 `result.querySources`。更新答案格式時，一起驗證群組推播、`/進度` 補送、引用「詳細」及 Issue 留言，避免讓讀者先看到內部版本資訊。
- **兩個專案的儲存庫名稱相同時**（不同組織），簡稱不算指名，這是刻意的。
- **追問沿用上一題的專案**（路由依據 `followup`）只由系統設定，AI 不能自己宣稱。條件：引用了機器人的回答（以 `notifications.sent_message_id` 對應），或 AI 判定接續 7 天內的上一題；本次沒有指名其他專案。對話串沒有題數上限，提示的最近 5 題給完整問答、更早的只給「先看重點」（`server/followup.ts` 的 `keyPointsOf`），不另外呼叫 AI 摘要。看板改接（`relinkTask`）不能接到自己的後續題，處理中的任務不能改。待確認中的上一題仍走「補充併入同一張任務」的舊流程。
- **回覆補問就是回答**：收訊時若引用的是本群組、目前版本的補問（`notifications.kind='group_question'`，`dedupe_key` 帶版本），直接以 `server/answers.ts` 的 `applyAnswer` 併進需求，不再進判讀、也不呼叫模型；舊版本的提問不會被套用。看板「送出回答」走同一個函式。
- **追加修改接在同一個 PR**：修改任務有 `parent_id`、上一題 `status=ready` 且 PR 仍開著（同儲存庫、分支相同、目標分支相同）時，派工以 PR head 為 `base_sha`、沿用上一題的分支，發布改用 `GitHub.continuePr`（快轉分支、PR 說明附上追加段落）。上一題還在 queued／running／reviewing／budget_wait 時先不執行。重試時若分支是上一題的、但 PR 已不能接續，就停下來請人確認，避免把舊 PR 當成這次的結果。
- **群組推播要記下 LINE 回傳的訊息 ID**（`sentMessages[0].id`）。少了它，成員引用機器人的回答時就認不出是哪一題。
- **用 reply token 補送通知（`/進度`）也要寫回訊息 ID**：`Line.reply` 回傳每則的 `sentMessages[i].id`，呼叫端依陣列索引寫回對應通知的 `sent_message_id`。同一個 reply token 只能用一次，所有內容必須合併成一個最多 5 則的 `messages` 陣列，不能分兩次回。補送前在收訊交易內用 `claimPendingGroupReplies`（`FOR UPDATE OF n SKIP LOCKED` 並先設 `sent_at`）佔住，reply 失敗或逾時再把 `sent_at` 還原。原因：沒寫回 ID，補送的答案打「詳細」、補送的問題用「回覆」作答都接不上；不先佔住，`flushNotifications` 會在同一時間再推一次。
- **`/進度` 佔住的通知要能自己回來、壞掉的那則要隔離**：佔住（收訊交易內）與寫回 reply 結果（交易提交後）之間程序可能中止，`flushNotifications` 每輪開頭以 `reclaimStaleClaims` 把停在 `claimingNote` 超過 2 分鐘、沒有 `sent_message_id` 的列放回待送（兩分鐘是尚未送出的領取期限。送出前須比對 PostgreSQL 保存的完整領取時間，並鎖住通知列直到寫回結果；回收與推播用 `SKIP LOCKED` 略過送出中的批次。額度暫停時也會回收，讓成員可再次取回）。reply 被 LINE 以內容問題拒收（`replyRejected`：4xx，但不含 429、401／403 與「reply token」失效）時這批 `reply_failures+1`，到 2 次就改寫 `replyGaveUpNote`、不再被 `retrievable` 取回；5xx、逾時、沒有權杖不加。原因：reply token 一次只能用一次、整批一起成敗，一則讓 LINE 一直回 400 的內容會讓整個群組的 `/進度` 永遠失敗；token 失效、限流則是換一個 token 就好，算進去會冤枉正常的通知。
- **Discord 的 `/進度` 先提交領取交易，再送出摘要與通知**。補送時逐則核對領取時間，只鎖正在送出的通知列，寫回訊息識別碼後才標記同任務的舊通知已被取代。新通知已被領取時，另一個 `/進度` 和背景推播都要等補送結果，再決定是否送出同任務的舊通知。送出失敗就歸還尚未送達的通知，遇到 429 依 Discord 指定的等待時間延後，兩種失敗次數都維持原值。共用的 `reclaimStaleClaims` 會回收 LINE 和 Discord 已領取、逾時且沒有訊息識別碼的通知。原因是 Discord 送訊等待期間，同頻道收訊仍須能鎖住群組列，回收也須避開正在送出的通知。
- **同一交易排入的通知 `created_at` 相同**（PostgreSQL 的 `now()` 是交易開始時間）：要挑「同一任務最新一則」時不能只比 `created_at`、`id`。例如 `approvalNotice` 的 `group_received` 和接著 `askInGroup` 的 `group_question` 同時間排入，`/進度` 以 `group_received` 排最後、再比時間與 `id`；標記較舊通知為已被取代時，也直接在 SQL 裡和佔住的列比較（含同一時間），不要把 `created_at` 傳回 JS 再比。原因：只比 `id`（隨機 UUID）時約一半機率挑到「收到」，補問被標成已被取代，群組再也拿不到要回答的問題；JS `Date` 只到毫秒，傳回資料庫比較會漏掉同一毫秒內的列。
- **補問共用憑證判定。** 看板輸入、LINE 引用作答、常見答案的通知文字及按鈕，都以同一規則檢查。成員引用本群組可辨識的補問且回答含憑證格式時，只保存固定提示及已處理狀態，避免原文進入聊天紀錄、需求版本、稽核或後續判讀。這項檢查也適用於停用群組與過期補問。過期補問的普通文字仍依原有流程當作補充。
- **「收到」的狀態判斷要和判讀排程一致**（`server/line.ts` 的 `honestAck`、`server/group-replies.ts` 的 `ackFor`）：沒有可用專案的條件與 `triage-window.ts` 的 `EXISTS(... p.enabled AND p.validated_at IS NOT NULL)` 相同，改一邊要同步另一邊。這些狀態只改回覆文字，不改 `eligible`、`processed`，專案恢復或解除暫停後訊息仍會被判讀。原因：兩邊條件不同時，「收到」會說已保留但永遠不處理，或說沒專案卻其實會處理。
- **引用追問入口與等待**：收訊以同群組、具任務的通知核對引用，記為 `command` 並保存 `messages.bot_reply`，避免通知清理改變等待時間。整批待判讀文字都是已核對引用時安靜 5 秒即可排程；混合批次維持 60／300 秒。排程與取得群組鎖後共用 `triage-window.ts` 的判斷，明確追問不等檔案索引完成。判讀失敗以獨立的 `triage_retry_at` 退避 60 秒，佇列重試、新收訊息與五分鐘上限都不能跳過；成功或人工恢復時清除。此暫時期限不納入備份。
- **定期檢查的排程只看 `tasks.check_draft`**：沒有它，需求再怎麼寫「每 15 分鐘」都只會當一般查詢回答一份方案，不會建立檢查。判讀沒聽到頻率時先填每 60 分鐘並列為假設，不為此發問；若還是問了，回答補問時以 `shared/checks.ts` 的 `parseSchedule` 讀出排程補進 `check_draft`（只在補問是在問頻率時，避免把答案裡剛好出現的時間誤當排程）。專案沒有登記資料庫連線時，提示會告訴 Codex（`checkDraft.databaseConnection=false`）優先擬 HTTP／TCP；只有擬出 SQL 或沒有擬出有效定義時才附上 `noConnectionHint`，請管理者到看板專案頁設定（HTTP、TCP 檢查用不到資料庫連線，附上提醒只會誤導）；帳密只在看板輸入、加密保存，不從聊天收。
- **依任務狀態而變的判讀規則由程式算好再交給模型**（`server/triage.ts` 的 `absorbsFollowups`、`existingTaskView`）：`existingTasks[].followup` 標明補充會併入（`merge`）或另開一題（`separate`），併入流程也用同一個判斷。原因：只在提示寫「狀態為 awaiting_approval 時合併」，模型把已核准任務的追加也寫成合併版本，同一項修改在父子兩張單各做一次（#236）。

- **環境設定的檔案摘錄只保留原文行、不改寫，而且先掃描完整內容再摘錄**（`server/setup-excerpt.ts`）。系統以 `includes` 比對 AI 引用的 evidence，改寫過的摘要會讓正確的引用被拒絕；先摘錄再掃描則會漏掉省略段落裡的憑證。過大或略過的檔案一律記在 `omissions`，看板照實列出，不要為了「看起來完整」偷偷丟掉。
- **重新驗證遇到暫時性問題不停用專案**（`Execution.validate` 的失敗分支）：已驗證通過的專案，失敗原因經 `classifyFailure` 判定為暫時性（AI 服務、訂閱讀取、網路、執行器逾時）時，沿用先前的設定、命令與啟用狀態，只記下原因。原因：部署後驗收時主機記憶體不足，Codex 讀不到訂閱額度十多分鐘，一次重新驗證就把能用的專案停用了。專案或設定本身的失敗（測試沒過、找不到測試命令）照舊停用。
- **專案驗證進度以佇列狀態為準**（`server/validation-queue.ts`）：排程、去重與等鎖交接都以同版設定仍在排隊、重試或執行中的工作為準。進度隨工作保存，`projects.setup_status` 保存驗證結果或補問。原因：工作結束、過期或設定升版後，畫面才能移除「驗證中」，也能接受下一次驗證。
- **專案腳本自己啟動 SQL Server 時，系統不接手**（`server/sqlserver-test.ts` 的 `selfManagedSqlServer`）：自動模式下，腳本（不含 CI 與文件）出現 `sqlservr` 或 `/opt/mssql/bin` 就不提供系統的 SQL Server，照專案腳本跑。原因：系統接手時提示 AI 不可自行啟動 sqlservr，AI 就不能用專案腳本，只好給不出測試命令（驗收時 DcMateH5Api 因此驗證失敗）。管理者選「一律提供」時仍提供。
- **只能在特定外部環境跑的測試照 CI 排除**（`server/project-setup.ts` 的指示）：README、CI 或測試程式寫明只在某台伺服器或指定資料庫執行、要靠環境變數指定外部連線才啟用的測試，AI 不可自行設定那個環境變數或導向容器資料庫，改用 `verification=partial` 並寫出排除了哪些測試。原因：驗收時 AI 把只能對 MES_TEST 跑的測試導向容器內的空資料庫，造成假失敗並停用專案。
- **LocalDB 導向：字串只有伺服器名稱時只換位址**（`worker/mssql/sqlserver.mjs` 的 `rewriteLocalDb`、`builderCredentials`）。原因：`SqlConnectionStringBuilder { DataSource = @"(localdb)\MSSQLLocalDB" }` 被換成整串連線字串後，DataSource 變成無效的伺服器名稱（SqlClient error 25），WeYuJetOpcUaLoader 因此驗證失敗。屬性寫的 `IntegratedSecurity = true` 一併改成 sa 帳號；物件初始設定式不能重複指定同一屬性，所以已有 `TrustServerCertificate` 就不再加。改了這兩個函式要重建 `line-agentflow-worker-mssql:local`。
- **衍生映像的鍵看套件識別，不看安裝指令**（`server/derived-image.ts` 的 `packageIdentity`）：只用名稱、來源、版本與基底映像。原因：每次重新驗證 AI 都會重寫安裝指令的措辭，以整份指令為鍵時同一組套件一天重建了 8 個映像。建置失敗不留映像，所以重用的一定是裝好的。
- **驗證失敗的錯誤保留例外訊息**（`server/failure.ts` 的 `failureDigest`）：先挑整段輸出的例外訊息與失敗測試，再接輸出結尾。只取結尾時，真正的 SQL 錯誤會被堆疊擠掉。
- **環境驗證的安裝、測試指令失敗用白話說明，建議對應專案頁的按鈕**（`ValidationPhaseError`、`classifyFailure(…, "validation")`）：`validation_error` 存「分類：白話說明。／錯誤重點：…／建議：…」，原始輸出摘要接在 `--- 原始輸出摘要 ---` 這一行之後（畫面可收合）。任務用的建議（「按重試」「看執行紀錄」）在專案頁沒有對應按鈕，所以規則另有 `validation` 建議；新增分類規則時若會出現在安裝或測試輸出，也要寫。其他驗證錯誤本身已是整理過的說明，只去掉「Error: 」前綴，不再分類（分類會把它們打成「預期外的錯誤」）。
- **執行中途停止要說出原因**（`Execution.execute` 的 `assertCurrent` 與 `stopReason`）：監看計時器發現暫停、設定變更、群組停用或逾時時會請執行器停掉容器，執行器只回「工作已取消」；catch 改用記下的原因分類，執行紀錄仍保留原始訊息。系統暫停（`PausedStop`）把任務放回排隊、不算失敗也不推失敗通知，恢復後照常經過預算與同時執行檢查。專案 `config_version` 改變時，資料庫觸發器 `invalidate_project_confirmations` 會先把執行中的任務改回待確認並寫下原因，結束時的失敗更新不會蓋掉它；測試要模擬「設定被變更」時用群組或專案停用。原因：管理者只是按暫停或停用群組、專案，任務就被標成「系統發生預期外的錯誤」並推給群組。
- **中斷回收不能卡住排程器**（`server/jobs.ts` 的 `recoverRun`）：先收回憑證，再以 20 秒逾時取消；取消失敗只記錄、留到下一輪。只有任務真的從執行中轉為失敗時才通知「執行曾中斷」，收尾時取消失敗留下的紀錄（任務已回答或待合併）只收尾。原因：沿用預設 30 分鐘逾時或讓例外往外丟，通知、派工與佇列心跳會一起停擺；已完成的任務被叫去重試會重跑一次、浪費額度。

## 8. 用假群組模擬 LINE 測試

要在正式環境驗證判讀或查詢行為、又不想打擾真實群組時：

1. 用正式的 LINE Channel Secret 簽章，把事件 POST 到 `http://127.0.0.1:4310/webhooks/line`，群組 ID 用虛構的 `C` 開頭 33 字元字串。腳本只在記憶體讀取 secret，不輸出。
2. 新群組預設停用；由人在看板「群組」頁啟用並綁定專案。
3. 同一個問題送第二次會被判為「重複需求」，驗證時要換新的問法。
4. 測試結束後由人在看板停用假群組，並拒絕留下的待確認任務。
5. 送出索取機密的測試題時，確認它停在待確認；若意外被排程，立即用「撤回」事件停下。

## 9. Windows 與殼層

| 規則                                                                                          | 原因                                                                                                                                                                           |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 在 Git Bash 執行 `docker compose exec` 帶路徑參數時加 `MSYS_NO_PATHCONV=1`。                  | Git Bash 會把 `/data/...` 改寫成 Windows 路徑。                                                                                                                                |
| 查資料庫用 `docker compose exec -T db psql -U agentflow -d agentflow`（在部署目錄）。         | 正式資料庫不發布主機連接埠。                                                                                                                                                   |
| Windows PowerShell 5.1 沒有 `&&`、`??`；寫腳本以 Node 為主。                                  | 部署腳本要在預設環境就能執行。                                                                                                                                                 |
| 重新載入 egress 的白名單用 `kill -HUP "$(cat /tmp/squid.pid)"`，不用 `squid -k reconfigure`。 | Squid 在容器內是 PID 1，`squid -k` 會以「PID 值太小」拒絕執行。                                                                                                                |
| Linux 主機目前不能部署。                                                                      | `app` 經 `host.docker.internal` 連主機執行器、開機啟動只支援 Windows 工作排程器。                                                                                              |
| 常駐的排程工作（監督程序、自備通道）經 `conhost.exe --headless` 執行，不直接執行 `node.exe`。 | 直接執行會開出可見的主控台視窗；視窗被人或桌面自動化工具關掉時，監督程序連同執行器與通道一起被結束（2026-11-17 正式入口因此中斷）。`npm run deploy` 偵測到舊設定會自動改註冊。 |
| Windows 開發機的 PDF 文字層測試會略過，除非另外安裝 poppler（`pdfinfo` 與 `pdftotext`）。 | Git for Windows 只附 xpdf 版 `pdftotext`、沒有 `pdfinfo`，`server/document-text.ts` 讀 PDF 要兩者都有；正式映像（`Dockerfile`）有安裝 poppler，不受影響。 |
