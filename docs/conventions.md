# 專案慣例與注意事項

這份文件收集「不寫下來就容易踩到」的規則：哪些事一定要一起改、哪些指令不能在哪裡執行、哪些錯誤其實是正常現象。人和 AI 代理在這個儲存庫工作前都應該讀過一次；發現新的潛規則就補在這裡，不要只留在對話或個人筆記。

每條規則都附上原因。原因不再成立時，連同規則一起刪掉。

## 1. 語言與協作

| 規則                                                                                                                                                                                                           | 原因                                                                                    |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 文件、使用者介面、Issue、PR、commit 訊息一律使用繁體中文。                                                                                                                                                     | 使用者與維護者都以繁體中文溝通；混用語言會讓看板與通知不一致。                          |
| commit 與 PR 標題用 [Conventional Commits](https://www.conventionalcommits.org/zh-hant/) 格式：`類型: 說明`。類型用英文小寫，說明用繁體中文，例如 `fix: 查詢的機密判斷只看使用者原文`。                        | 一眼看出每次變更的性質，也方便產生版本說明。                                            |
| 常用類型：`feat` 新功能、`fix` 修正、`docs` 文件、`refactor` 重構、`test` 測試、`perf` 效能、`ci` CI 設定、`chore` 其他雜項。不相容的變更在類型後加 `!`（例如 `feat!:`），並在內文寫 `BREAKING CHANGE:` 說明。 | 統一用詞；不相容的變更（例如新增必填設定）要讓部署者一眼看到。                          |
| 先開 Issue 寫規格，再開 PR 實作；PR 說明寫 `Closes #N`（完成）或「關聯 #N」（部分）。                                                                                                                          | 規格與決策要能回頭查。GitHub 只認英文關鍵字，寫中文「關閉 #N」不會自動關閉 Issue。      |
| PR 以 **Squash and merge** 合併，合併後的 commit 標題就是 PR 標題（`類型: 說明 (#N)`）。                                                                                                                       | `main` 上每個 commit 都是一個完整、格式一致的變更，部署與回溯都靠 `git log --oneline`。 |
| PR 說明分「改了什麼」「驗證」「待人工確認」三段。                                                                                                                                                              | 審查者先看結論；需要人或正式環境才能確認的事項不能被淹沒。                              |

## 2. 兩個目錄：部署目錄與開發目錄

同一台主機上至少有兩份程式碼：

- **部署目錄**：有 `.local/secrets.json` 的那一份。監督程序每 30 秒用這裡的 `compose.yaml` 執行 `docker compose up -d`。
- **開發目錄**：另外 `git clone` 或 `git worktree add ..\chat2pr-dev -b 分支 origin/main` 建立。

| 規則                                                                                                         | 原因                                                                                          |
| ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 部署目錄只用 `npm run deploy` 更新，不在裡面切分支、改檔或 commit。                                          | 在這裡切到改過 `compose.yaml` 的分支，正式容器會在 30 秒內被重建。                            |
| 部署目錄固定停在分離 HEAD 的 `origin/main`，不需要本機 `main` 分支。                                         | 本機 `main` 可能被其他工作目錄佔用；`npm run deploy` 一律 `git switch --detach origin/main`。 |
| 開發目錄不要執行 `docker compose up`、`down`、`build app`。                                                  | Compose 專案名稱固定為 `line-agentflow`，從開發目錄執行會動到正式容器。                       |
| 開發目錄可以 `docker build -f worker/Dockerfile -t <臨時標籤> .`，但不要覆寫 `line-agentflow-worker:local`。 | `:local` 是正式執行器使用的工作映像；開發分支的映像蓋上去等於未經部署就上線。                 |
| `npm run deploy` 在開發目錄會拒絕執行。                                                                      | 開發目錄沒有 `.local/secrets.json`，這是刻意的保護。                                          |

| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |

| 備份內容                                                              | `scripts/backup.ts` 與 `scripts/restore.ts` 的版本號與相容處理                                                                                                                   | 舊備份必須仍能還原，並提示缺少的資料。                                                                                                           |
| 對外文件提到的指令或路徑                                              | `README.md` 與 `docs/` 中所有出現處                                                                                                                                              | 部署手冊是給人和 AI 代理照著執行的；過期指令會直接造成事故。                                                                                     |
| 新增 PostgreSQL advisory lock 編號                                    | 先搜尋既有編號（`rg "7346[0-9]"`），派工相關的集中在 `server/capacity.ts`                                                                                                        | 編號相同的鎖會互相等待：搶執行位置若和訂閱額度檢查共用 73466，額度查詢的網路等待會卡住所有派工。                                                 |
| 專案顯示名稱（目前是 chat2pr）                                        | **不要**跟著改內部識別名稱：Compose 專案 `line-agentflow`、容器、資料卷、映像標籤、排程工作 `LINE-AgentFlow`，以及寫進目標專案 AGENTS.md 的段落標題 `## LINE-AgentFlow 專案記憶` | 資料卷名稱一改，正式資料就接不上；排程工作改名會讓開機恢復失效；段落標題是用來找回既有段落的標記，改了會重複寫入。這些識別名稱固定不變是刻意的。 |

## 4. 測試

| 規則                                                                                                                                                                                                                            | 原因                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 修改後執行 `npm run typecheck` 與相關測試；交付前執行 `npm test` 與 `npm run build`。                                                                                                                                           | CI 會再跑一次，但本機先擋下能省一輪等待。                                                           |
| 測試資料庫是 `db-test`（`127.0.0.1:5439`，資料在記憶體）；和正式服務同一台主機時它通常已在執行，不要再從開發目錄啟動。                                                                                                          | 見第 2 節：從開發目錄 `compose up` 會動到正式容器。                                                 |
| 多個工作樹同時跑測試時，用 `docker run --rm --tmpfs /var/lib/postgresql/data -p 127.0.0.1:<其他埠>:5432 pgvector/pgvector:pg17`（虛構帳密、資料庫名稱以 `_test` 結尾）另開臨時資料庫，以 `TEST_DATABASE_URL` 指過去，測完停掉。 | 共用的 `db-test` 被其他工作樹同時遷移、清空時會出現 `deadlock detected`，各分支的遷移也會互相疊加。 |
| 需要新工作映像的容器測試：先建臨時標籤，以 `ACCEPTANCE_WORKER_IMAGE=<臨時標籤>` 執行，測完刪除標籤。                                                                                                                            | 測試預設使用 `line-agentflow-worker:local`；提高 `WORKER_REV` 後舊映像會被拒絕。                    |
| 測試只用虛構憑證與虛構專案名稱。                                                                                                                                                                                                | 機密與客戶資訊不得進入 Git；測試快照也算。                                                          |
| 依建立順序比對的查詢要 `ORDER BY created_at`，不要依 uuid。                                                                                                                                                                     | uuid 沒有順序，會讓測試時好時壞。                                                                   |
| 測試不要直接 import `src/app/*`。                                                                                                                                                                                               | 前端使用 `@/` 路徑別名，vitest 的伺服器端設定不解析它。                                             |
| 定期檢查環境的真實 Docker 測試：用法見 `tests/check-environments.test.ts` 開頭。                                                                                                                                                | 需要先建檢查映像；找不到映像時整組略過。                                                            |
| Prettier 只對自己改過的檔案執行，不要對 `server/*.ts` 整批格式化。                                                                                                                                                              | 整批格式化會改到無關檔案，PR 差異失焦。                                                             |

## 5. 機密與權限

| 規則                                                                                                           | 原因                                                                       |
| -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 機密只由人在 `npm run setup` 的本機設定頁輸入；不要貼進對話、Issue、PR 或日誌。                                | 對話與日誌會被保存、轉傳或送進模型。                                       |
| 不要讀出或印出 `.env`、`.local/`、`.codex-service/`、`.local/setup-url.txt` 的內容；需要用到時只在指令中引用。 | 同上；`setup-url.txt` 內含一次性權杖。                                     |
| LINE 使用者 ID 只留在伺服器端，不回傳瀏覽器。                                                                  | 屬於個人識別資訊。                                                         |
| 不可繞過登入、人工審核、預算、版本檢查或容器隔離；核准、改設定一律經看板。                                     | 這些是系統的安全邊界。直接改資料庫核准任務，會讓稽核紀錄失真。             |

## 6. 部署與維運時的「正常現象」

| 現象                                                          | 說明                                                                              |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 部署後冒煙測試提醒「系統」頁的 `codex_subscription_gate` 異常 | 部署重啟執行器的瞬間讀不到 Codex 額度；約一分鐘後自動恢復。持續異常才需要處理。   |
| 部署結束提醒「重新驗證專案」                                  | 工作映像有更新；到「專案」頁對受影響的專案按「AI 自動設定並驗證」或「驗證環境」。 |
| `npm run deploy` 拒絕執行，說有排隊或執行中的任務             | 刻意的保護，等任務結束或在看板取消後再部署。                                      |
| 看板「HTTPS 入口」短暫異常                                    | 通道狀態檔超過 180 秒沒更新就會顯示異常；通道重新連線後會恢復。                   |
| 群組回覆「收到」不計入 LINE 推播額度，其他群組回覆會計入      | 「收到」使用 reply token；其他是推播，依群組人數計算。                            |

## 7. AI 判讀與查詢的規則

這些規則改過不只一次，修改前先讀對應的測試（`tests/query-routing.test.ts`、`tests/project-confirmation.test.ts`）。

- **修改任務一律人工確認**，不論風險或專案是否明確。
- **判讀補問與假設**：`question` 只能是一個問題（常見答案最多三個），`assumptions` 保存可修正且有依據的預設；系統把假設統一附加在摘要中，沿用 `task_versions` 保存版本。查詢一律移除開發方案；修改只有產品方向不同時提供方案、唯一推薦與理由。未回答任務的單一假設修改會產生新版本、保留未解問題並作廢舊核准；已回答查詢改為沿用對話串建立追問，保留原回答。方案與問題的跨欄位不符由 `clarifyDecision()` 修正並留下「已調整 AI 輸出」稽核，不讓可修正的輸出造成整批判讀失敗。單一方案改為確認問題，不擅自採用為假設。整份需求編輯以使用者摘要為準並清除舊結構標記，避免兩份內容不一致。
- **備份第 4 版**包含任務的問題與假設；還原第 1～3 版時新欄位使用預設值並提示核對原摘要。
- **查詢可以自動執行**的條件：本次訊息明確指名專案（完整儲存庫、專案名稱，或在已登記專案中唯一且至少 6 個字的儲存庫名稱／去括號名稱），或有唯一的檔案證據；並且沒有要求交出機密實際值。
- **機密判斷只看使用者原文**，不看 AI 改寫的摘要與驗收（AI 常寫「列出…」「提供…」，會造成誤判）。AI 列出的風險只當提醒，除非寫明「要求揭露／輸出」。
- **跨專案查詢**：指名的專案都必須綁定本群組；其他專案的原始碼唯讀放在 `/agentflow/env/projects/<儲存庫名稱>`。
- **兩個專案的儲存庫名稱相同時**（不同組織），簡稱不算指名，這是刻意的。
- **追問沿用上一題的專案**（路由依據 `followup`）只由系統設定，AI 不能自己宣稱。條件：引用了機器人的回答（以 `notifications.sent_message_id` 對應），或 AI 判定接續 7 天內的上一題；本次沒有指名其他專案。對話串沒有題數上限，提示的最近 5 題給完整問答、更早的只給「先看重點」（`server/followup.ts` 的 `keyPointsOf`），不另外呼叫 AI 摘要。看板改接（`relinkTask`）不能接到自己的後續題，處理中的任務不能改。待確認中的上一題仍走「補充併入同一張任務」的舊流程。
- **回覆補問就是回答**：收訊時若引用的是本群組、目前版本的補問（`notifications.kind='group_question'`，`dedupe_key` 帶版本），直接以 `server/answers.ts` 的 `applyAnswer` 併進需求，不再進判讀、也不呼叫模型；舊版本的提問不會被套用。看板「送出回答」走同一個函式。
- **追加修改接在同一個 PR**：修改任務有 `parent_id`、上一題 `status=ready` 且 PR 仍開著（同儲存庫、分支相同、目標分支相同）時，派工以 PR head 為 `base_sha`、沿用上一題的分支，發布改用 `GitHub.continuePr`（快轉分支、PR 說明附上追加段落）。上一題還在 queued／running／reviewing／budget_wait 時先不執行。重試時若分支是上一題的、但 PR 已不能接續，就停下來請人確認，避免把舊 PR 當成這次的結果。
- **群組推播要記下 LINE 回傳的訊息 ID**（`sentMessages[0].id`）。少了它，成員引用機器人的回答時就認不出是哪一題。
- **引用追問入口與等待**：收訊以同群組、具任務的通知核對引用，記為 `command` 並保存 `messages.bot_reply`，避免通知清理改變等待時間。整批待判讀文字都是已核對引用時安靜 5 秒即可排程；混合批次維持 60／300 秒。排程與取得群組鎖後共用 `triage-window.ts` 的判斷，明確追問不等檔案索引完成。判讀失敗以獨立的 `triage_retry_at` 退避 60 秒，佇列重試、新收訊息與五分鐘上限都不能跳過；成功或人工恢復時清除。此暫時期限不納入備份。
- **定期檢查的排程只看 `tasks.check_draft`**：沒有它，需求再怎麼寫「每 15 分鐘」都只會當一般查詢回答一份方案，不會建立檢查。判讀沒聽到頻率時先填每 60 分鐘並列為假設，不為此發問；若還是問了，回答補問時以 `shared/checks.ts` 的 `parseSchedule` 讀出排程補進 `check_draft`（只在補問是在問頻率時，避免把答案裡剛好出現的時間誤當排程）。專案沒有登記資料庫連線時，擬定結果一律附上 `noConnectionHint`，請管理者到看板專案頁設定；帳密只在看板輸入、加密保存，不從聊天收。

- **環境設定的檔案摘錄只保留原文行、不改寫，而且先掃描完整內容再摘錄**（`server/setup-excerpt.ts`）。系統以 `includes` 比對 AI 引用的 evidence，改寫過的摘要會讓正確的引用被拒絕；先摘錄再掃描則會漏掉省略段落裡的憑證。過大或略過的檔案一律記在 `omissions`，看板照實列出，不要為了「看起來完整」偷偷丟掉。

## 8. 用假群組模擬 LINE 測試

要在正式環境驗證判讀或查詢行為、又不想打擾真實群組時：

1. 用正式的 LINE Channel Secret 簽章，把事件 POST 到 `http://127.0.0.1:4310/webhooks/line`，群組 ID 用虛構的 `C` 開頭 33 字元字串。腳本只在記憶體讀取 secret，不輸出。
2. 新群組預設停用；由人在看板「群組」頁啟用並綁定專案。
3. 同一個問題送第二次會被判為「重複需求」，驗證時要換新的問法。
4. 測試結束後由人在看板停用假群組，並拒絕留下的待確認任務。
5. 送出索取機密的測試題時，確認它停在待確認；若意外被排程，立即用「撤回」事件停下。

## 9. Windows 與殼層

| 規則                                                                                  | 原因                                                                              |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 在 Git Bash 執行 `docker compose exec` 帶路徑參數時加 `MSYS_NO_PATHCONV=1`。          | Git Bash 會把 `/data/...` 改寫成 Windows 路徑。                                   |
| 查資料庫用 `docker compose exec -T db psql -U agentflow -d agentflow`（在部署目錄）。 | 正式資料庫不發布主機連接埠。                                                      |
| Windows PowerShell 5.1 沒有 `&&`、`??`；寫腳本以 Node 為主。                          | 部署腳本要在預設環境就能執行。                                                    |
| Linux 主機目前不能部署。                                                              | `app` 經 `host.docker.internal` 連主機執行器、開機啟動只支援 Windows 工作排程器。 |
