# 專案慣例與注意事項

這份文件收集「不寫下來就容易踩到」的規則：哪些事一定要一起改、哪些指令不能在哪裡執行、哪些錯誤其實是正常現象。人和 AI 代理在這個儲存庫工作前都應該讀過一次；發現新的潛規則就補在這裡，不要只留在對話或個人筆記。

每條規則都附上原因。原因不再成立時，連同規則一起刪掉。

## 1. 語言與協作

| 規則                                                                                                                                                                                                                            | 原因                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文件、使用者介面、Issue、PR、commit 訊息一律使用繁體中文。                                                                                                                                                                      | 使用者與維護者都以繁體中文溝通；混用語言會讓看板與通知不一致。                                                                                                                                                                                                                                          |
| commit 與 PR 標題用 [Conventional Commits](https://www.conventionalcommits.org/zh-hant/) 格式：`類型: 說明`。類型用英文小寫，說明用繁體中文，例如 `fix: 查詢的機密判斷只看使用者原文`。                                         | 一眼看出每次變更的性質，也方便產生版本說明。                                                                                                                                                                                                                                                            |
| 常用類型：`feat` 新功能、`fix` 修正、`docs` 文件、`refactor` 重構、`test` 測試、`perf` 效能、`ci` CI 設定、`chore` 其他雜項。不相容的變更在類型後加 `!`（例如 `feat!:`），並在內文寫 `BREAKING CHANGE:` 說明。                  | 統一用詞；不相容的變更（例如新增必填設定）要讓部署者一眼看到。                                                                                                                                                                                                                                          |
| 先開 Issue 寫規格，再開 PR 實作；PR 說明寫 `Closes #N`（完成）或「關聯 #N」（部分）。                                                                                                                                           | 規格與決策要能回頭查。GitHub 只認英文關鍵字，寫中文「關閉 #N」不會自動關閉 Issue。                                                                                                                                                                                                                      |
| PR 以 **Squash and merge** 合併，合併後的 commit 標題就是 PR 標題（`類型: 說明 (#N)`）。                                                                                                                                        | `main` 上每個 commit 都是一個完整、格式一致的變更，部署與回溯都靠 `git log --oneline`。                                                                                                                                                                                                                 |
| PR 說明分「改了什麼」「驗證」「待人工確認」三段。                                                                                                                                                                               | 審查者先看結論；需要人或正式環境才能確認的事項不能被淹沒。                                                                                                                                                                                                                                              |
| 看板表單會送到的 API 輸入檢查（zod），每條規則都要寫繁體中文訊息；子區塊的欄位在訊息前加區塊名稱（例如「SSH 連接埠請填 1–65535」）。                                                                                            | 看板只把 400 回應 `details` 裡含中文的提示接在「輸入格式錯誤」後面（`src/app/api-response.ts`），zod 的英文預設訊息與欄位路徑會被略過；沒寫中文訊息的規則，使用者只看到「輸入格式錯誤」，不知道哪一欄錯了。                                                                                             |
| `server/app.ts` 的 `app.setErrorHandler(replyError)` 必須在所有 `register*` 與 `app.get`／`app.post` 之前；新的 `register*` 一律放在它之後。                                                                                    | Fastify 的路由在註冊當下就取用當時的錯誤處理器，之後才呼叫 `setErrorHandler` 不會套到已註冊的路由。早於它的路由會回 Fastify 預設格式 `{ statusCode, error: "Bad Request", message }`，看板只讀 `error`，使用者只看到英文狀態名稱；成員、聊天室、專案資訊與資料庫連線的錯誤原因曾因此到不了畫面（#58）。 |
| `projects.validation_error` 除了驗證失敗原因，也用來放「請重新驗證」這類提醒；寫入不是失敗的提醒時，文字要放進 `shared/project-setup.ts` 的 `repoNotice`（或同類常數）並在 `src/app/project-form.ts` 的 `validationKind` 判斷。 | 專案頁看到 `validated_at` 為空又有 `validation_error` 就標「驗證失敗」（紅色徽章與提示）；儲存庫接回後的提醒曾因此被標成驗證失敗，管理者會以為環境壞了。                                                                                                                                                |

## 2. 兩個目錄：部署目錄與開發目錄

同一台主機上至少有兩份程式碼：

- **部署目錄**：有 `.local/secrets.json` 的那一份。監督程序每 30 秒用這裡的 `compose.yaml` 執行 `docker compose up -d`。
- **開發目錄**：另外 `git clone` 或 `git worktree add ..\chat2pr-dev -b 分支 origin/main` 建立。

| 規則                                                                                                         | 原因                                                                                          |
| ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 部署目錄只用 `npm run deploy` 更新，不在裡面切分支、改檔或 commit。                                          | 在這裡切到改過 `compose.yaml` 的分支，正式容器會在 30 秒內被重建。                            |
| 部署目錄固定停在分離 HEAD 的 `origin/main`，不需要本機 `main` 分支。                                         | 本機 `main` 可能被其他工作目錄佔用；`npm run deploy` 一律 `git switch --detach origin/main`。 |
| 開發目錄不要執行 `docker compose up`、`down`、`build app`。                                                  | Compose 專案名稱固定為 `line-agentflow`，從開發目錄執行會動到正式容器。                       |
| 開發目錄可以 `docker build -f worker/Dockerfile -t <臨時標籤> .`，但不要覆寫 `line-agentflow-worker:local`。 | `:local` 是正式執行器使用的工作映像；開發分支的映像蓋上去等於未經部署就上線。                 |
| `npm run deploy` 在開發目錄會拒絕執行。                                                                      | 開發目錄沒有 `.local/secrets.json`，這是刻意的保護。                                          |

## 4. 測試

啟動真實排程器的測試替身須依執行器端點回傳對應格式。即使只驗證判讀或派工，排程也會同步定期檢查環境；`checks/environments/sync` 沒有清除項目時仍須回傳 `{ removed: [] }`，否則測試可能通過卻在背景留下同步錯誤。

推播額度相關的潛規則（`server/line-quota.ts`、`shared/line-quota.ts`）：

- **額度用完不能計入 `attempts`**：每月上限要到下個月才恢復，算進失敗次數的話，每則通知約一分鐘內就撞滿 3 次被永久放棄。只有 429 加上 `monthly limit` 訊息才算額度用完；一般 429 是短時間限流，照舊累加。
- **恢復後不得補送過時的群組訊息**：解除暫停與按「重送」前都要先跑 `expireStaleNotifications`。群組推播依人數計費，幾週前的排隊說明、舊版補問一次推出去，新月份的額度當天就會用完，成員也會收到已經不對的內容。
- **額度狀態不可併進 `'line'` 檢查，也不放進 `server/health.ts` 的 critical 清單**：解除全域暫停要求 `'line'` 一天內正常，額度用完時收訊與「收到」其實照常，併進去會讓管理者連暫停都解不開；critical 會再排一則「服務異常」私訊，這時根本送不出去。
- **解除暫停只看 LINE 額度 API 的回報**，不用日期推算：LINE 換月的時區與方案升級都不在我們手上。額度 API 回應看不懂時當成「讀不到」，不能當成上限 0，否則會把推播整個停掉。
- **群組推播依人數計費，額度判斷要用剩餘則數對群組人數，不能只看 `used<limit`**：剩 5 則時推給 8 人的群組，LINE 一樣回 429 monthly limit。只看 `used<limit` 會每小時解除一次、又撞一次，排在後面的私訊也一起卡住。所以：
  - 解除暫停的條件仍是「剩 1 則以上」（私訊可送）；群組能不能送由 `flushNotifications` 逐則用 `quotaRemaining`（`line_quota` 說明裡的用量）對 `pushCost(groups.member_count)` 判斷，不夠就略過那個群組（不加 `attempts`，`last_error` 寫 `quotaShortForGroup`）。
  - 私訊與群組通知分開取：一起依 `created_at` 取 10 則時，被略過的群組通知會佔滿每一輪。
  - 每送一則就在本地把用量加上人數（未知時 1）並寫回說明，不必每則都查額度 API；連線檢查每小時再以 LINE 的回報校正。
  - 群組撞到 429 monthly limit 時先查額度 API：還剩 1 則以上只是不夠這個群組，本輪略過群組、私訊照送，並把這個群組記成「至少剩餘＋1 人」（`markGroupTooLarge`），24 小時內不再對它撞 429；剩 0 則、查不到或私訊也撞到才整個封鎖。
  - 封鎖時要保留用量（`markQuotaExhausted` 沒給用量就沿用原說明解析出的），看板才顯示得出「本月已用 X／上限 Y」。
  - 因人數不夠而略過的群組通知，續送前要先跑 `expireQuotaHeld`（`last_error` 以 `quotaShortPrefix` 開頭、這輪不再略過的群組，過時的標成已過期）。原因：這種略過不會進入 `line_quota` 封鎖，`syncLineQuota` 解除封鎖時的 `expireStaleNotifications` 管不到；大群組可能被略過幾週，換月額度一恢復就會把舊說明推給整個群組。還在略過的群組不動，成員仍可用 `/進度` 取回 7 天內的回覆。
- **群組人數 API（`/v2/bot/group/{id}/members/count`、聊天室用 `/v2/bot/room/{id}/members/count`）不計推播額度，但仍要快取 24 小時**：通知排程每 20 秒跑一輪，每輪都查會無謂地打 LINE；只有剩餘額度已知且有上限時才需要人數。

## 7. AI 判讀與查詢的規則

這些規則改過不只一次，修改前先讀對應的測試（`tests/query-routing.test.ts`、`tests/project-confirmation.test.ts`）。

- **修改任務一律人工確認**，不論風險或專案是否明確。
- **判讀補問與假設**：`question` 只能是一個問題（常見答案最多三個），`assumptions` 保存可修正且有依據的預設；系統把假設統一附加在摘要中，沿用 `task_versions` 保存版本。查詢一律移除開發方案；修改只有產品方向不同時提供方案、唯一推薦與理由。未回答任務的單一假設修改會產生新版本、保留未解問題並作廢舊核准；已回答查詢改為沿用對話串建立追問，保留原回答。方案與問題的跨欄位不符由 `clarifyDecision()` 修正並留下「已調整 AI 輸出」稽核，不讓可修正的輸出造成整批判讀失敗。單一方案改為確認問題，不擅自採用為假設。整份需求編輯以使用者摘要為準並清除舊結構標記，避免兩份內容不一致。
- **備份第 4 版**包含任務的問題與假設；還原第 1～3 版時新欄位使用預設值並提示核對原摘要。
- **查詢可以自動執行**的條件：本次訊息明確指名專案（完整儲存庫、專案名稱，或在已登記專案中唯一且至少 6 個字的儲存庫名稱／去括號名稱），或有唯一的檔案證據；並且沒有要求交出機密實際值。
- **機密判斷只看使用者原文**，不看 AI 改寫的摘要與驗收（AI 常寫「列出…」「提供…」，會造成誤判）。AI 列出的風險只當提醒，除非寫明「要求揭露／輸出」。
- **跨專案查詢**：指名的專案都必須綁定本群組；其他專案的原始碼唯讀放在 `/agentflow/env/projects/<儲存庫名稱>`。
- **兩個專案的儲存庫名稱相同時**（不同組織），簡稱不算指名，這是刻意的。
- **追問沿用上一題的專案**（路由依據 `followup`）只由系統設定，AI 不能自己宣稱。條件：引用了機器人的回答（以 `notifications.sent_message_id` 對應），或 AI 判定接續 7 天內的上一題；本次沒有指名其他專案。對話串沒有題數上限，提示的最近 5 題給完整問答、更早的只給「先看重點」（`server/followup.ts` 的 `keyPointsOf`），不另外呼叫 AI 摘要。看板改接（`relinkTask`）不能接到自己的後續題，處理中的任務不能改。待確認中的上一題仍走「補充併入同一張任務」的舊流程。
- **回覆補問就是回答**：收訊時若引用的是本群組、目前版本的補問（`notifications.kind='group_question'`，`dedupe_key` 帶版本），直接以 `server/answers.ts` 的 `applyAnswer` 併進需求，不再進判讀、也不呼叫模型；舊版本的提問不會被套用。看板「送出回答」走同一個函式。
- **追加修改接在同一個 PR**：修改任務有 `parent_id`、上一題 `status=ready` 且 PR 仍開著（同儲存庫、分支相同、目標分支相同）時，派工以 PR head 為 `base_sha`、沿用上一題的分支，發布改用 `GitHub.continuePr`（快轉分支、PR 說明附上追加段落）。上一題還在 queued／running／reviewing／budget_wait 時先不執行。重試時若分支是上一題的、但 PR 已不能接續，就停下來請人確認，避免把舊 PR 當成這次的結果。
- **群組推播要記下 LINE 回傳的訊息 ID**（`sentMessages[0].id`）。少了它，成員引用機器人的回答時就認不出是哪一題。
- **用 reply token 補送通知（`/進度`）也要寫回訊息 ID**：`Line.reply` 回傳每則的 `sentMessages[i].id`，呼叫端依陣列索引寫回對應通知的 `sent_message_id`。同一個 reply token 只能用一次，所有內容必須合併成一個最多 5 則的 `messages` 陣列，不能分兩次回。補送前在收訊交易內用 `claimPendingGroupReplies`（`FOR UPDATE OF n SKIP LOCKED` 並先設 `sent_at`）佔住，reply 失敗或逾時再把 `sent_at` 還原。原因：沒寫回 ID，補送的答案打「詳細」、補送的問題用「回覆」作答都接不上；不先佔住，`flushNotifications` 會在同一時間再推一次。
- **`/進度` 佔住的通知要能自己回來、壞掉的那則要隔離**：佔住（收訊交易內）與寫回 reply 結果（交易提交後）之間程序可能中止，`flushNotifications` 每輪開頭以 `reclaimStaleClaims` 把停在 `claimingNote` 超過 2 分鐘、沒有 `sent_message_id` 的列放回待送（reply 本身 5 秒逾時，2 分鐘足以排除進行中的補送；額度暫停時也照做，那時 `/進度` 是唯一的取回管道）。reply 被 LINE 以內容問題拒收（`replyRejected`：4xx，但不含 429、401／403 與「reply token」失效）時這批 `reply_failures+1`，到 2 次就改寫 `replyGaveUpNote`、不再被 `retrievable` 取回；5xx、逾時、沒有權杖不加。原因：reply token 一次只能用一次、整批一起成敗，一則讓 LINE 一直回 400 的內容會讓整個群組的 `/進度` 永遠失敗；token 失效、限流則是換一個 token 就好，算進去會冤枉正常的通知。
- **同一交易排入的通知 `created_at` 相同**（PostgreSQL 的 `now()` 是交易開始時間）：要挑「同一任務最新一則」時不能只比 `created_at`、`id`。例如 `approvalNotice` 的 `group_received` 和接著 `askInGroup` 的 `group_question` 同時間排入，`/進度` 以 `group_received` 排最後、再比時間與 `id`；標記較舊通知為已被取代時，也直接在 SQL 裡和佔住的列比較（含同一時間），不要把 `created_at` 傳回 JS 再比。原因：只比 `id`（隨機 UUID）時約一半機率挑到「收到」，補問被標成已被取代，群組再也拿不到要回答的問題；JS `Date` 只到毫秒，傳回資料庫比較會漏掉同一毫秒內的列。
- **含憑證的補問回答不能落到追問路徑**：引用本群組補問、回答含憑證格式時，訊息只存 `redact` 後的文字、`trigger_mode='chat'`、`processed=true`，回 `credentialAnswerAck` 後直接 return。原因：落到 botReply 會被存成 `command` 交給判讀模型（判讀送的是原文），還回「收到，我接著上一題處理」讓成員以為已收下。過期補問（已有人回答或需求改版）不在此列，照舊當補充送判讀。
- **「收到」的狀態判斷要和判讀排程一致**（`server/line.ts` 的 `honestAck`、`server/group-replies.ts` 的 `ackFor`）：沒有可用專案的條件與 `triage-window.ts` 的 `EXISTS(... p.enabled AND p.validated_at IS NOT NULL)` 相同，改一邊要同步另一邊。這些狀態只改回覆文字，不改 `eligible`、`processed`，專案恢復或解除暫停後訊息仍會被判讀。原因：兩邊條件不同時，「收到」會說已保留但永遠不處理，或說沒專案卻其實會處理。
- **引用追問入口與等待**：收訊以同群組、具任務的通知核對引用，記為 `command` 並保存 `messages.bot_reply`，避免通知清理改變等待時間。整批待判讀文字都是已核對引用時安靜 5 秒即可排程；混合批次維持 60／300 秒。排程與取得群組鎖後共用 `triage-window.ts` 的判斷，明確追問不等檔案索引完成。判讀失敗以獨立的 `triage_retry_at` 退避 60 秒，佇列重試、新收訊息與五分鐘上限都不能跳過；成功或人工恢復時清除。此暫時期限不納入備份。
- **定期檢查的排程只看 `tasks.check_draft`**：沒有它，需求再怎麼寫「每 15 分鐘」都只會當一般查詢回答一份方案，不會建立檢查。判讀沒聽到頻率時先填每 60 分鐘並列為假設，不為此發問；若還是問了，回答補問時以 `shared/checks.ts` 的 `parseSchedule` 讀出排程補進 `check_draft`（只在補問是在問頻率時，避免把答案裡剛好出現的時間誤當排程）。專案沒有登記資料庫連線時，提示會告訴 Codex（`checkDraft.databaseConnection=false`）優先擬 HTTP／TCP；只有擬出 SQL 或沒有擬出有效定義時才附上 `noConnectionHint`，請管理者到看板專案頁設定（HTTP、TCP 檢查用不到資料庫連線，附上提醒只會誤導）；帳密只在看板輸入、加密保存，不從聊天收。

- **環境設定的檔案摘錄只保留原文行、不改寫，而且先掃描完整內容再摘錄**（`server/setup-excerpt.ts`）。系統以 `includes` 比對 AI 引用的 evidence，改寫過的摘要會讓正確的引用被拒絕；先摘錄再掃描則會漏掉省略段落裡的憑證。過大或略過的檔案一律記在 `omissions`，看板照實列出，不要為了「看起來完整」偷偷丟掉。
- **重新驗證遇到暫時性問題不停用專案**（`Execution.validate` 的失敗分支）：已驗證通過的專案，失敗原因經 `classifyFailure` 判定為暫時性（AI 服務、訂閱讀取、網路、執行器逾時）時，沿用先前的設定、命令與啟用狀態，只記下原因。原因：部署後驗收時主機記憶體不足，Codex 讀不到訂閱額度十多分鐘，一次重新驗證就把能用的專案停用了。專案或設定本身的失敗（測試沒過、找不到測試命令）照舊停用。
- **專案腳本自己啟動 SQL Server 時，系統不接手**（`server/sqlserver-test.ts` 的 `selfManagedSqlServer`）：自動模式下，腳本（不含 CI 與文件）出現 `sqlservr` 或 `/opt/mssql/bin` 就不提供系統的 SQL Server，照專案腳本跑。原因：系統接手時提示 AI 不可自行啟動 sqlservr，AI 就不能用專案腳本，只好給不出測試命令（驗收時 DcMateH5Api 因此驗證失敗）。管理者選「一律提供」時仍提供。
- **只能在特定外部環境跑的測試照 CI 排除**（`server/project-setup.ts` 的指示）：README、CI 或測試程式寫明只在某台伺服器或指定資料庫執行、要靠環境變數指定外部連線才啟用的測試，AI 不可自行設定那個環境變數或導向容器資料庫，改用 `verification=partial` 並寫出排除了哪些測試。原因：驗收時 AI 把只能對 MES_TEST 跑的測試導向容器內的空資料庫，造成假失敗並停用專案。
- **驗證失敗的錯誤保留例外訊息**（`server/failure.ts` 的 `failureDigest`）：先挑整段輸出的例外訊息與失敗測試，再接輸出結尾。只取結尾時，真正的 SQL 錯誤會被堆疊擠掉。
- **環境驗證的安裝、測試指令失敗用白話說明，建議對應專案頁的按鈕**（`ValidationPhaseError`、`classifyFailure(…, "validation")`）：`validation_error` 存「分類：白話說明。／錯誤重點：…／建議：…」，原始輸出摘要接在 `--- 原始輸出摘要 ---` 這一行之後（畫面可收合）。任務用的建議（「按重試」「看執行紀錄」）在專案頁沒有對應按鈕，所以規則另有 `validation` 建議；新增分類規則時若會出現在安裝或測試輸出，也要寫。其他驗證錯誤本身已是整理過的說明，只去掉「Error: 」前綴，不再分類（分類會把它們打成「預期外的錯誤」）。
- **執行中途停止要說出原因**（`Execution.execute` 的 `assertCurrent` 與 `stopReason`）：監看計時器發現暫停、設定變更、群組停用或逾時時會請執行器停掉容器，執行器只回「工作已取消」；catch 改用記下的原因分類，執行紀錄仍保留原始訊息。系統暫停（`PausedStop`）把任務放回排隊、不算失敗也不推失敗通知，恢復後照常經過預算與同時執行檢查。專案 `config_version` 改變時，資料庫觸發器 `invalidate_project_confirmations` 會先把執行中的任務改回待確認並寫下原因，結束時的失敗更新不會蓋掉它；測試要模擬「設定被變更」時用群組或專案停用。原因：管理者只是按暫停或停用群組、專案，任務就被標成「系統發生預期外的錯誤」並推給群組。
- **中斷回收不能卡住排程器**（`server/jobs.ts` 的 `recoverRun`）：先收回憑證，再以 20 秒逾時取消；取消失敗只記錄、留到下一輪。只有任務真的從執行中轉為失敗時才通知「執行曾中斷」，收尾時取消失敗留下的紀錄（任務已回答或待合併）只收尾。原因：沿用預設 30 分鐘逾時或讓例外往外丟，通知、派工與佇列心跳會一起停擺；已完成的任務被叫去重試會重跑一次、浪費額度。

## 8. 用假群組模擬 LINE 測試

要在正式環境驗證判讀或查詢行為、又不想打擾真實群組時：

1. 用正式的 LINE Channel Secret 簽章，把事件 POST 到 `http://127.0.0.1:4310/webhooks/line`，群組 ID 用虛構的 `C` 開頭 33 字元字串。腳本只在記憶體讀取 secret，不輸出。
2. 新群組預設停用；由人在看板「群組」頁啟用並綁定專案。
3. 同一個問題送第二次會被判為「重複需求」，驗證時要換新的問法。
4. 測試結束後由人在看板停用假群組，並拒絕留下的待確認任務。
5. 送出索取機密的測試題時，確認它停在待確認；若意外被排程，立即用「撤回」事件停下。
