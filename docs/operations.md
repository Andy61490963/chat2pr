# 維運

服務上線後的日常運作、處理方式與已知邊界。安裝、升級、備份還原與疑難排解的指令在 [部署手冊](deployment.md)。

## 自動運作與限制

系統頁的「Codex 訂閱推論」區分正常、異常、未確認。成功與失敗以目前模型的實際推論為準；派工或記憶體暫停、額度阻擋、沒有目前模型的讀數、讀數過期或無法取樣時，顯示未確認及原因，不發停擺警告，也不覆蓋上次推論證據。按「檢查連線」不會額外消耗推論額度。

啟動後讀取資料庫的最後確認時間，沒有讀數才立即檢查。正常時每六小時檢查一次。工作失敗可提早檢查，但兩次探測至少相隔十五分鐘；探測中不再排一次。首次失敗即更新系統頁，十五分鐘後確認持續異常才發通知。若仍異常，兩小時後檢查恢復情形，之後每六小時再查。修改或審查階段已有成功推論證據時直接更新健康狀態，不必等排程，也不花探測次數。

每個臺北日最多送出 8 次探測，最後 2 次保留給已有失敗讀數的模型確認恢復。啟動、定期、換模型、失敗補測共用資料庫計數與最短間隔；已送出的失敗也算，重啟不歸零。探測採低推理強度，避免將預設推理用量誤判成故障。每次探測只向代理送一個請求；上游回報 401 且成功換發憑證時，代理最多重送一次。

輸入固定為「1」，指令固定為「只輸出數字 1。」；不附歷史或工具。代理只接受上游回報輸入不超過 128、輸出不超過 64 個 token 的結果。串流文字達 256 個 UTF-8 位元組就中止。這是本地驗收上限，不是上游計費上限；已產生的 token 仍可能消耗訂閱額度。每次期限 45 秒，回應資料上限 64 KiB。探測不建立工作容器、不占使用者每日派工次數。系統頁記錄成功或失敗、延遲與代理能確認的原因。

安裝、升級、備份還原、停止與疑難排解的指令都在[部署手冊](deployment.md)。日常只需要知道：

- 監督程序每 30 秒檢查一次服務，Docker Desktop、容器、執行器或通道停了會自動拉回來（自備的通道程序停了，會重新啟動它的排程工作，見部署說明的「看門狗」）；它由 Windows 排程工作 `LINE-AgentFlow` 在登入後以 `conhost.exe --headless` 啟動，桌面上不會出現視窗，也就不會因為誤關視窗而停掉。要在前景觀察可執行 `npm run services`。
- 升級用 `npm run deploy`；想確認服務是否正常，隨時可以執行 `npm run smoke`。
- 部署要重啟主機程序時，停掉監督程序之前會先查排程工作 `LINE-AgentFlow` 的狀態。排程工作已停用或不存在時先印出提醒，重啟改為直接在背景啟動監督程序；排程工作啟動後 20 秒內沒有出現監督程序，也改用直接啟動，並印出走了哪條路。部署以失敗結束時，最後列出監督程序、執行器與 app 哪些停著，以及恢復指令。
- 排程工作已停用時，主機現在雖然照常執行，重開機後卻不會自動啟動任何東西。冒煙測試的「開機自動啟動」會提醒（不算失敗）；修復用 `npm run install:startup` 重新註冊，或 `Enable-ScheduledTask -TaskName 'LINE-AgentFlow'`。照部署手冊「停止與移除」暫時停止服務後，恢復時記得也要重新啟用排程工作。
- 每天自動清理一次 Docker：刪除超過 14 天、沒有專案或容器在用的 `line-agentflow-app`／`line-agentflow-worker` 舊標籤（`:latest`、`:local` 一律保留），清除懸空映像與超過 7 天沒用到的建置快取。不刪資料卷，也不動其他專案有名稱的映像；結果寫在看板的活動紀錄。只有正式實例的執行器會動手。這是既有行為，可在看板「系統」頁的「Docker 磁碟」關閉；其他清理規則見下方〈Docker 磁碟〉。
- 連線中斷、上游暫時無法服務這類錯誤會自動重新排隊，同一需求版本最多兩次，期間不發失敗通知；第三次仍失敗才通知。同一任務的失敗通知 30 分鐘內最多一則。
- 獨立審查只有「需要修改程式或交付內容才能解決」的問題會擋下發布；需要人、正式環境或真實資料才能完成的驗收會列在 PR 的「待人工確認」，合併前請自行檢查。
- 整台主機或入口斷線時 `app` 發不出通知，要靠[外部健康監控](deployment.md#外部健康監控)。
- HTTPS 入口每分鐘探測一次，異常與恢復各需連續兩次讀數確認。中斷未滿五分鐘就恢復時，只能在收件匣的「顯示系統紀錄」查看這次中斷。探測確認中斷已滿五分鐘時，鈴鐺會顯示異常，確認恢復後再顯示一則恢復通知。服務再次探測確認中斷滿 15 分鐘後，才會納入 LINE 私訊摘要。全通知模式也會納入這類中斷的恢復通知。使用每小時連線檢查的服務，會在下一次實際探測後確認。
- 主機記憶體不足時立刻暫停派新工作，系統頁即時顯示原因；暫停持續滿 10 分鐘才通知一次「服務異常：主機資源」，回升到 2.5 GB 以上並穩定 5 分鐘後恢復派工，再通知一次恢復。記憶體在門檻附近擺動時維持暫停，不會每幾分鐘切換一次。
- 查看日誌：`docker compose logs --tail 100 app`、`.local\runner.log`、`.local\tunnel.log`。看板「系統」頁的「容器與磁碟」分頁列出各服務狀態。
- 「容器與磁碟」分頁的執行器狀態分三種：
  - **連線正常**：執行器與 Docker 都有回應。
  - **執行器沒有回應**（紅色）：主機上的執行器程序（4312）完全沒有 HTTP 回應。監督程序每 30 秒會自動拉起，可執行 `npm run services` 在前景觀察。
  - **Docker 沒有回應**（黃色）：執行器正常，但 Docker 回報錯誤或超過 20 秒沒有回應（執行器另以不碰 Docker 的 `/alive` 確認自己還在）。先確認 Docker Desktop 有在跑、主機可用記憶體是否太低。
  - 後兩種情況下，服務與工作容器清單保留上一次成功讀到的資料，並標示「資料停在 X 分鐘前」。
- 系統頁「執行」分頁的「同時執行」卡片有兩組記憶體數字：
  - **Windows 主機記憶體**：執行器在 Windows 上讀 `os.freemem()`。暫停派工**只看這個**（低於 2 GB 暫停、回升到 2.5 GB 恢復）。
  - **Docker（WSL）可用／共**：app 容器讀自己的 `/proc/meminfo`，就是工作容器實際所在的 Docker VM 的數字，標「僅供參考」。Windows 會把 vmmem 佔住的記憶體算成已用，所以兩者可能差很多；目前只記錄、不參與判斷。要改成用 VM 可用量判斷前，先在忙碌與閒置時段各記錄一段兩組數字（見 `docs/conventions.md` 第 3 節）。

看板支援全域暫停、專案停用、取消與重試。設定的「AI 與執行」分頁提供「暫停新需求判讀」：LINE 收訊與圖片下載照常，尚未判讀的訊息保留，已核准的任務仍可執行。儲存取消暫停後，才恢復彙整待處理訊息。已送出的判讀不承諾即時取消，但設定變更前的晚到結果不會建立或修改任務；全域暫停仍優先停止判讀與派工。新安裝及升級預設不啟用這個獨立開關。

設定頁有兩種變更會先跳確認框，寫出影響才儲存：容器網路從「隔離」改成「完全開放」，以及 AI 模式從訂閱改成 API。按取消不送出任何變更，表單內容保留；確認後稽核紀錄寫出每個欄位變更前後的值。

全系統同時執行的任務數由系統頁「同時執行」設定（預設 2、最多 8）；主機記憶體不足時暫停派新工作（見上方）。每個任務時間上限預設 30 分鐘，可在設定頁調低（最多 30 分鐘）。訂閱模式以每日執行次數上限控管（預設 20 次）；API 模式預估上限為每次 US$3、每日 US$15，價格為應用程式估算，不保證供應商帳單絕不超額。兩者皆依臺北午夜重算。

訂閱模式也可在「Codex 訂閱額度」設定「保留給你個人使用」，接受 0–90 的整數，預設 0。任一 Codex 額度視窗的用量達到 100% 減去保留比例時，判讀、開發、驗證與查詢會等待額度，畫面顯示保留比例及已知的重置時間。系統確認各視窗用量低於上限且帳號仍可使用時，自動繼續工作。管理者變更保留比例會清除舊的額度判定，活動紀錄會寫下操作者及變更前後的比例。

原始訊息與圖片依設定保留（預設 30 天）；撤回立即清除內容，相關需求重新審核。每天凌晨 3 點備份非原文資料並保留 7 份。專案的資料庫連線與結構快照不進備份，還原後到專案詳情重新登記並擷取。
備份加密使用本機 `sessionSecret`，請另外安全保存 `.local/secrets.json`，否則無法還原。

備份第 5 版包含待挑選清單；第 4 版包含需求的問題與假設；第 3 版已有成員名單、群組綁定、群組記憶與專案知識，還原後可重新建立向量。還原第 1～4 版時，待挑選清單為空。還原第 1～3 版時，問題與假設使用空值並提示核對原摘要。第 2 版備份沒有成員名單，還原後只有擁有者能登入，需重新加入成員；第 1 版另缺多專案綁定與記憶，須在啟用前由管理者核對。

## 更新連線金鑰

由 `ADMIN_GITHUB_ID` 指定的擁有者使用 GitHub 登入後，在十分鐘內開啟看板「設定」的「連線與金鑰」分頁，在「連線金鑰」卡片更新。逾時時從畫面重新登入，回到同一分頁後重新輸入。

- 可更新 LINE Channel Secret、LINE Channel Access Token、Discord 機器人權杖、Discord 應用程式 ID、OpenAI API 金鑰。欄位留空會保留原值；Discord 的兩個選填項目可勾「移除」。
- 按「更新」並核對確認對話框所列欄位。看板只顯示設定狀態和最後更新時間；舊設定沒有更新紀錄。看板更新會留下操作者與欄位名稱，並依管理者通知設定排送私訊。
- LINE 與 OpenAI 在下次呼叫時讀取新值。Discord 在權杖或應用程式 ID 變更時會關閉舊連線並套用新設定，可從「服務連線」查看結果。
- GitHub App／OAuth、`sessionSecret`、公開網址與通道設定由主機的 `npm run setup` 維護。這些設定若有誤，可能讓公開入口或登入失效。

若看板顯示金鑰已寫入但未能保存變更紀錄，請先檢查資料庫連線，並以「最後更新」和「最近動態」核對主機寫入及稽核結果。若主機程序曾在寫入時中斷，確認主機執行器與本機設定頁都已停止後，才能清除遺留的 `.local/secrets.json.lock` 或該次暫存檔。

## Discord 連線

1. 到 [Discord 開發者入口](https://discord.com/developers/applications) 建立應用程式。從「一般資訊」複製應用程式 ID。到「機器人」頁產生權杖，並在特殊 Gateway 讀取權限中開啟「讀取訊息內容」（Message Content Intent）。
2. 由擁有者到看板「連線金鑰」填寫應用程式 ID 與機器人權杖。也可透過 `npm run setup` 的本機設定頁填寫。若誤貼成 OAuth2 用戶端密鑰，請到開發者入口的「Bot」頁按 Reset Token，複製新的機器人權杖。
3. 在 Discord 應用程式的「安裝」頁開啟伺服器安裝，加入機器人與斜線指令範圍（`bot`、`applications.commands`），勾選檢視頻道、讀取訊息歷史、傳送訊息、建立公開討論串、在討論串中傳送訊息、加入反應、嵌入連結及附加檔案。複製安裝連結，由有管理伺服器權限的人開啟並選擇伺服器。若頻道有個別權限，確認機器人能在該頻道讀取與回覆，並確認成員能使用應用程式指令。使用私人討論串時，請把機器人加入該討論串，讓它可以收訊及回覆。

   新舊 Discord 頻道預設從 `/任務` 或提及機器人的需求開公開討論串；斜線指令使用互動回覆作為入口。後續通知回到該串。無法開串時仍在頻道回覆；請在看板「群組」選取頻道，查看「回覆位置」下的權限提示。要保留原本的回覆方式，選「回覆在頻道」並儲存變更。
4. 在普通文字或公告頻道送一則訊息。看板「群組」會顯示以「伺服器／#頻道」命名的新群組，預設停用且不回覆。綁定可用專案並啟用後，才會判讀後續需求。指令模式接受文字指令、提及機器人及引用任務回覆。

設定應用程式 ID 後，機器人連線時會註冊 `/任務`（必填「需求」）及 `/進度`。若未填應用程式 ID，請傳送以 `/任務` 或 `/進度` 開頭的文字訊息。開啟頻道回覆後，選「收到需求時也回覆」會在原訊息加上 ✅；補問、查詢答案、完成和失敗說明會引用原訊息。已不存在的原訊息無法加反應，其他回覆會改貼到原頻道。成員可以按補問的常見答案，或直接回覆機器人。斜線 `/進度` 用 Discord 互動回覆取回本頻道的進度及近期有效的未送達通知。

Discord 沒有每月推播額度。遇到速率限制時，系統依 Discord 指定的等待時間延後重試，保留原有失敗次數。其他送達原因可在看板的聊天室與任務詳情查看。

公開、私人與公告討論串沿用父頻道的啟用、觸發、專案綁定及回覆設定。由討論串提出的需求會在該討論串回覆，使用 `/進度` 也會取回目前所在頻道或討論串的回覆。直接回覆補問，或在該補問開出的討論串傳送答案，都能接續同一題。

### 管理者通知

在看板「設定」的「通知」分頁找到「管理者通知」，選擇 LINE 或 Discord 並產生配對碼。10 分鐘內在該平台的機器人私訊傳送 `配對 <代碼>`，配對完成後即可儲存通知目的地。代碼可使用一次。兩個平台的既有綁定會保留，待確認、失敗與補問等私訊依目前儲存的平台送出。Discord 私訊逐則排送，LINE 私訊使用既有摘要與額度設定。看板鈴鐺可查看完整通知。

可在設定頁的「連線與金鑰」分頁查看 Discord 狀態。Gateway 長連線由 app 主動連出，Discord 收訊無須新增公開網址或 Webhook。發生斷線時 app 會嘗試重連，也會繼續處理其他服務。若狀態持續中斷，確認主機可連出至 Discord、權杖有效，並檢查是否開啟讀取訊息內容。要停用 Discord，由擁有者在「連線金鑰」移除機器人權杖。

文字、支援格式的附圖及發言者名稱沿用聊天室的保存期限。收到刪除事件時，來源和相關任務依撤回規則處理；收到編輯事件時，若來源已用於判讀，相關任務會依撤回規則回到人工審核，更新後的訊息則依群組觸發方式重新入列。

## 使用摩擦指標

看板「設定」頁的「使用摩擦」卡片，衡量使用者有沒有感覺到流程，可依期間（7／30／90 天）與群組篩選。全部從既有的任務、稽核紀錄、通知與訊息計算，不另外記錄資料。

| 指標               | 怎麼算                                                                                   | 方向     |
| ------------------ | ---------------------------------------------------------------------------------------- | -------- |
| 每件任務需要人回應 | 核准、拒絕、補充、指定專案、採用方案、修改假設、回答補問、改接、追加等稽核紀錄的平均次數 | 越少越好 |
| 每件任務要切到看板 | 同上，但不含在 LINE 回答補問                                                             | 越少越好 |
| 重講背景           | 沒有接上前一題、30 分鐘內又在同群組明確指名同一專案的任務數                              | 越少越好 |
| 接錯題             | 使用者改接對話串的次數                                                                   | 越少越好 |
| 第一則群組訊息     | 從訊息送出到機器人第一則群組推播的中位數；用 reply token 回的「收到」不留紀錄，不含在內  | 越短越好 |
| 查詢拿到答案       | 從提出到回答的中位數                                                                     | 越短越好 |
| 修改返工率         | 已合併的修改中，7 天內同一需求又追加修改的比例                                           | 越低越好 |

## Docker 磁碟

看板「系統」頁的「容器與磁碟」分頁（`/system?tab=disk`）包含「Docker 磁碟」卡片。分頁標籤上的數字會加總異常服務、仍有專案使用的過舊映像，以及磁碟空間不足的提醒。

- **用量**：映像、容器、資料卷、建置快取的數量、在用數、大小與可回收空間，算法與 `docker system df` 相同。「可回收」是 Docker 的估算，包含正式資料庫等不會刪的未掛載資料卷。
- **歸屬**：每個映像、容器、資料卷都標出用途（工作映像、專案衍生映像、服務映像、工作容器、任務工作區、正式資料庫、服務資料與備份、原始碼快取、套件快取，或「無法確認歸屬」），依 `io.agentflow.*` 與 Compose 標籤判斷。
- **空間提醒**：每小時維護時檢查 Docker 磁碟與主機磁碟，取較緊的一顆。可用空間低於提醒門檻（預設 15%）時私訊管理者一次；回升到門檻再多 1 個百分點才通知恢復，避免來回洗版。
- **暫停派工（預設關閉）**：開啟後，可用空間低於暫停門檻（預設 5%）時新工作留在佇列不執行，系統頁會說明原因，空間回升後自動恢復。關閉時只通知。狀態超過 3 小時沒更新（例如執行器失聯）就不擋派工。
- **清理規則（預設全部關閉）**：每條規則要管理者在系統頁開啟才生效，開啟後每天自動執行一次並寫進活動紀錄：
  - 已結束任務的工作區資料卷：結束後保留 3 天（可調）；執行中、保留期內、找不到執行紀錄的不清。
  - 停止的工作容器：本實例、執行已結束的才清。
  - 沒有專案使用的舊工作映像：本系統的 app／worker 映像與專案衍生映像，沒有專案設定使用、沒有容器在用、建立超過 14 天（可調）；`:local`、`:latest` 一律保留。
  - 建置快取：超過上限（預設 20 GB）時從最舊的清起。
- **盤點失敗時**：卡片顯示「目前無法盤點 Docker」並提示檢查服務；「立即清理」會在確認前重新盤點。提醒與清理規則存在資料庫（`GET /api/system/disk/settings` 直接讀取、不呼叫執行器），仍可調整與儲存。Docker 恢復後按「重新盤點」。
- **立即清理**：先重新盤點並列出會刪除的項目（依各規則目前的條件，不論是否開啟），管理者勾選類別、確認後才刪，結果與操作者寫進活動紀錄。確認後才變動的項目不會被刪。
- **永不刪除**：正式資料庫、服務資料與備份、原始碼快取、套件快取，以及無法確認歸屬的資源，任何規則與「立即清理」都只列出不刪；執行器刪除前也會再核對一次。刪除映像與容器都不加 force，仍在使用時 Docker 會拒絕。
- 任務工作區另有既有的 30 天保留：執行結束 30 天後由每小時維護清除（含執行結果），不受上面的規則開關影響。
- 只有正式實例的執行器會刪除；驗收實例共用同一個 Docker 時只盤點。

## 定期檢查

看板「定期檢查」頁可以設定每隔一段時間（最短 15 分鐘）或每天固定時間執行的檢查，狀態改變時才通知：

- **需處理**：清單預設顯示全部。選「需處理」即可集中查看設備異常、連線缺失及系統無法執行的檢查，展開該列可查看原因。篩選會保存在網址。
- **三種檢查**：
  - SQL 唯讀查詢：使用專案登記的資料庫連線，只允許單一 SELECT，並包在一定回滾的交易中；
  - HTTP 健康檢查：非 2xx、逾時，或回應不含指定文字就算異常；
  - TCP 連線檢查。
  - HTTP、TCP 檢查拒絕本機回環、主機內部名稱與雲端中繼資料位址。
- **專用檢查環境**：每個檢查在自己的檢查容器執行，容器只拿到那一組連線，網路只通到那一個目標的那一個連接埠（細節見[架構說明](architecture.md#定期檢查環境)）。
  - 執行完先保留，下次同一個檢查直接重用；閒置超過設定時間（預設 2 小時）或保留數超過上限（預設 20 個）才清除，在「系統」頁「網路」分頁的「定期檢查環境」調整。
  - 檢查被修改、暫停、刪除或因錯誤停用，資料庫連線更新或刪除，群組停用、專案停用或解除綁定、系統暫停時立即清除；下次執行時以新設定重建。
  - 「定期檢查」頁展開檢查可看到環境狀態（未建立、保留中與預計清除時間、建立失敗與原因），也可以按「立即清除環境」。建立與清除都記在活動紀錄。
  - 顯示「找不到定期檢查映像」或「版本過舊」時，以 `npm run deploy` 更新（會建置 `line-agentflow-check:local`）；處理方式見下方「系統設定問題」。
- **從 LINE 提出**：在群組說「/任務 每小時檢查一次機台有沒有斷線」，判讀會記下排程並建立一題「草擬定期檢查」的查詢；Codex 依程式碼與資料庫結構快照選擇 SQL、HTTP 或 TCP 檢查並說明依據，系統據此建立待核准的檢查並試跑一次，回答與私訊會附上試跑結果。不符合規則的定義（例如會寫入的 SQL）不會被建立。
- **核准後才執行**：新建或修改後都是「待核准」，可以先「試跑」看結果；修改任何欄位都要重新核准。
  - 試跑結果顯示在該檢查的試跑按鈕旁（正常、異常或執行失敗，附時間），只留在畫面上，不寫進執行紀錄、不通知。
  - **SQL 檢查要先在專案頁登記資料庫連線才能核准**：沒有連線的專案仍可先儲存 SQL 檢查（例如保留 AI 草擬的定義），但核准與恢復會被拒絕，卡片會標示「缺少資料庫連線」並連到專案頁。
  - SQL 檢查的判定欄位要和查詢結果的欄位一致（大小寫不同可以）。查詢有回傳資料卻找不到判定欄位時，試跑顯示執行失敗並列出可用欄位，排程執行則算檢查本身出錯；查詢沒有回傳資料時維持「（無資料）」。列出欄位找不到只會在摘要提示，不影響判定。
- **執行時不呼叫 AI、不用 Codex 額度**。結果保留 30 天，不進每日備份。
- **通知**：
  - 只在變成異常或恢復正常時通知，持續異常不重複；
  - 預設發到群組並私訊管理者，靜音時段只通知管理者；
  - 每個檢查每天最多 6 則。
- **異常時請 AI 調查**：可選擇自動建立唯讀查詢任務調查可能原因，結果照查詢回報。每個檢查每天最多一次，會用 Codex 額度。通知只在真的建立調查時才寫「AI 正在調查可能原因，結果會再回報」；24 小時內已調查過會寫明這次不重複調查，專案停用或未驗證時不提調查。
- **檢查本身出錯**（連不上資料庫、SQL 錯誤、判定欄位找不到、檢查執行逾時）連續 3 次就暫停，只通知管理者，不會誤報成設備異常。
  - SQL 檢查的錯誤會說清楚是哪一種：欄位或資料表不存在（附名稱）、語法錯誤、沒有 SELECT 權限、資料表被其他交易鎖住超過 5 秒、查詢超過 60 秒未完成、其他被資料庫拒絕的查詢（附錯誤代碼）。只有還沒連上資料庫時，才會說登入、加密連線、主機或 SSH 跳板的問題。
  - 展開檢查可直接看到最近 5 次的時間、結果（正常／異常／執行失敗）與摘要，其餘可再展開；手機上不必懸停。
- **系統問題不計入連續失敗**：執行器連不上，或執行器、檢查環境回報暫時無法執行（環境建立失敗、啟動逾時、檢查容器連不上、環境已停止等 502／503 錯誤）時，仍記一筆執行失敗，摘要開頭是「系統暫時無法執行（不計入連續失敗）」，但不累計也不歸零連續失敗、不暫停。
  - 依連續次數延後 5、15、30 分鐘，之後每 60 分鐘重試（不晚於原本的下次排程）；系統恢復後自動繼續，不必逐一按「恢復」。
  - 「定期檢查」列標示「系統無法執行」，展開後可查看原因與重試時間。連續超過 6 小時會寫一筆活動紀錄，詳情會提醒到「系統」頁確認執行器與 Docker。
- **系統設定問題（要管理者處理，不會自己好）**：同樣不計入連續失敗、不改檢查狀態，但摘要開頭改為「系統設定問題（不計入連續失敗）」，重試間隔拉長到「下次排程」與「6 小時後」取較晚者。第一次發生時私訊管理者一則並寫活動紀錄（同一種問題每天一則，不是每個檢查各一則）；「定期檢查」頁頁首會顯示問題與處理方式，各檢查標示「系統無法執行」，展開可查看等待排除的問題。
  - **找不到定期檢查映像／映像版本過舊**：在部署目錄執行 `npm run deploy`，會重建 `line-agentflow-check:local`。
  - **定期檢查網路的位址已用完**：到「系統」頁「網路」分頁的「定期檢查環境」調低保留數上限或閒置時間，讓閒置環境先被清除；或在主機執行器的環境變數把 `CHECK_SUBNET_POOL` 改成更大的網段（每個環境佔一段 /28），再 `npm run deploy`。
  - **定期檢查網路位址與其他網路重疊**：把 `CHECK_SUBNET_POOL` 改成不和公司內網、Docker 其他網路重疊的網段（細節見[架構說明](architecture.md#定期檢查環境)），再 `npm run deploy`。
  - 排除後檢查會在下一次重試時自動繼續；想立刻確認，可在檢查上按「試跑」，或先「暫停」再「恢復」讓它立即執行。
- **自動暫停**：群組停用、專案停用或解除綁定、系統暫停時不執行；恢復後不補跑錯過的次數。

## 推播額度用完時

LINE 官方帳號每月的推播則數有上限，群組推播依群組人數計算。群組發言可帶回「收到」與待送通知。這些回覆免費。同一群組的首批付費推播立即送出，之後兩分鐘內的通知累積到下一批。每批最多五則訊息，只按收件人數計費一次。

**額度剩不多時的表現**

- 系統先送群組，再用更新後的本月用量判斷是否送私訊摘要。每批群組推播按人數計費，一則私訊摘要計一則。系統向 LINE 查群組人數，快取 24 小時。讀不到時沿用既有資料，一小時後再查。從未取得人數的群組先以 8 人估算；若 LINE 曾因額度不足拒收，估值至少高於當時的餘額。設定頁會標示估算人數。
- 管理者可在「設定」的「通知」分頁找到「LINE 推播」，調整私訊範圍和保留比例，變更記在活動紀錄。取得用量後，預設用到月上限的 30% 就暫停私訊（含測試通知），把剩餘額度留給群組。若下一則會侵占保留額度，系統會先暫停。設定 0% 時，私訊仍適用剩餘兩成的通知分級，設定 100% 時也會暫停無上限方案的私訊。尚未取得用量時，照常嘗試私訊，由 LINE 回應判定是否已達月上限。
- 第一件符合條件的私訊會在排程處理時立即推播。上一則成功送出後未滿 10 分鐘的通知，會等滿 10 分鐘再合併成一則，列出最多 5 件和看板連結，超出的件數可到鈴鐺查看。額度恢復後只整理 24 小時內的私訊。
- 剩下的則數不夠某個群組的人數時，那個群組的通知先不送，不計失敗次數；看板通知的錯誤欄寫「推播額度剩 X 則，不足這個群組 Y 人，額度恢復後再送」。人數較少的群組仍可推播，私訊仍須符合保留門檻。
- 剩餘額度到兩成，或這次推播會動用最後兩成時，付費額度留給補問、指令判讀結果、查詢答案、PR、結案結果、待處理失敗與檢查異常。中間進度只等免費回覆；有效期間內可由群組發言或輸入 `/進度` 取回。管理者私訊仍受既有的群組保留比例限制。
- 某個群組因額度不足被 LINE 拒收，但查到月額度仍有餘額時，暫緩本輪其餘群組推播。系統記下該群組至少需要的額度，等人數 API 回報後再更新。私訊仍須符合保留門檻。
- 額度恢復（換月、升級方案）後，下一次連線檢查寫入新用量，被略過的群組通知就自動續送；續送前一樣先把過時的（規則同下方「恢復」）標成「已過期，未補送」，不會把幾週前的說明推給整個群組。

**額度用完時的表現**

- LINE 推播回 429 且訊息是「You have reached your monthly limit.」，而且向 LINE 查到剩 0 則（或查不到、或連私訊也被拒絕）時，系統判定本月額度用完。設定的「連線與金鑰」分頁中，「LINE 推播額度」顯示異常、仍顯示本月用量，看板鈴鐺頂端多一行「LINE 推播額度用完，群組有人發言時會補送重要通知，看板通知照常」，各頁上方也有黃色橫幅說明替代做法（看鈴鐺、到任務詳情複製結果貼到群組、群組成員打 `/進度` 取回）。
- 額滿期間停止付費推播，重要通知留在佇列。啟用回覆的群組下次有人發言時，機器人用同一次免費回覆帶出仍有效的通知。若按鈕或訊息數量超出單次容量，回覆會提示其餘項目，成員可以打 `/進度` 取回原訊息。
- 「LINE 推播（群組回覆與私訊）」健康項維持原狀，不會顯示成連線異常；「LINE」連線檢查也照常，解除全域暫停不受影響。
- 「重送」與「送一則測試通知」停用，管理 API 回 409 並說明是額度問題、權杖沒有問題。
- 一般的 429（短時間送太快）不算額度用完，照舊重試 3 次。
- 若推播回應遺失，重試沿用原鍵。若 LINE 明確拒收整批內容，就在當輪的請求上限內拆開逐則傳送，每個成功的請求各按群組人數計費。若月額度封鎖時先前批次仍未確認收件，改用免費回覆可能讓成員再看到一次相同結果。

**恢復**

- 每小時的連線檢查（或在設定頁按「檢查連線」）會向 LINE 查本月上限與用量，這兩支 API 不計入額度。在設定的「通知」分頁可查看本月已用量與上限。用量可供估算時，看板以本月平均每日用量預估用完日；實際能否恢復推播仍以 LINE 回報為準。
- 查到還有額度（或方案沒有上限）才解除整體暫停，換月與方案升級都以 LINE 回報為準。群組要有足夠人數額度才送，私訊要低於保留門檻才送。
- 解除時先把過時的通知標成「已過期，未補送」，看板與鈴鐺仍查得到內容：
  - 群組的排隊說明、「收到，等管理者確認」：超過 6 小時，或任務已不在等待中；
  - 群組補問：任務不再等回答，或已經不是目前版本的問題；
  - 群組的失敗通知：任務已不是失敗狀態；
  - 其他群組通知：超過 24 小時；
  - 管理者私訊：超過 24 小時的不補送，從看板鈴鐺查看，系統會留下彙整提醒（全通知模式可把提醒納入私訊摘要）。
- 其餘的通知自動續送。

**重送**

設定頁的「重送」只重排重試 3 次仍失敗的通知，送出前會跳確認框，寫出私訊與群組各幾則、略過幾則已過期的。重送前同樣先套用上面的過期規則。稽核紀錄寫明操作者與三個數字。

## 日常處理

收件匣的「卡住的任務」每分鐘檢查一次。它只讀取任務、派工條件、服務與執行紀錄，並保存目前的提醒；不派工、不開容器、不呼叫模型，每次消耗的使用者執行次數與推論額度都是零。暫停派工或記憶體不足時仍能說明原因，不會解除暫停。

| 何時出現 | 下一步 |
| --- | --- |
| 排隊或等待額度滿 10 分鐘 | 依列出的派工、資源、專案綁定、執行器或額度原因處理。查不到阻擋原因時會明說，不會當作執行器已離線。 |
| 執行或審查的心跳超過 30 秒未更新，或超出該次期限 2 分鐘 | 查看該任務的執行紀錄。心跳逾時不等於容器已停止，仍由原本的回收流程核對任務鎖，不強制取消或重跑。 |
| 等待審核、補問、選擇專案、方案或待合併滿 24 小時 | 到任務詳情回答、決定或確認 PR；最後一次更新後重新計時。 |
| 同一專案最近 3 次已結束的執行都有同類失敗，最新任務仍是失敗 | 查看該筆執行。訂閱錯誤用執行器記下的固定類別，其他錯誤只用該次失敗稽核的分類；中間有成功或沒有分類證據就不列。 |

同一任務版本停在同一狀態再滿 10 分鐘才排一則管理者摘要；原因改變只更新說明，不重新計時或重送。同批卡住的任務合併通知，不逐筆推播。收件匣顯示總數與最早卡住的 20 筆；連續失敗只檢查最近 24 小時內結束的工作。解決的提醒會離開收件匣；摘要中的任務都已解除時不再補送。管理者私訊沿用既有的 LINE 或 Discord 摘要與額度規則，不通知群組。

- 待審核：檢視來源、缺漏與敏感理由；先補充缺漏，再核准目前版本。核准舊版本會被拒絕。
- 敏感路徑：實際修改新增敏感檔案時會再次要求核准，核准僅涵蓋列出的路徑。核准後從記錄的基底建立隔離副本，寫回送審的那份修改，接續測試與獨立審查，不重新修改。
- 開發失敗：保留工作資料卷與執行紀錄，最多自動修復一次。人工重試前會核對 GitHub 遠端分支與 PR。
- 接續已完成的修改：暫停、逾時或其他中斷前已收集到修改、且還沒有驗證結論時，同一需求版本與基底的下一次執行（恢復派工、重試、敏感路徑核准）把那份修改寫回新的隔離副本、重新安裝依賴，從測試與獨立審查接續；第一次驗證沒過、修復途中中斷時，帶著審查意見直接修復。自動修復仍只有一次，修復後仍沒過、SQL Server 複驗沒過、被機密檢查擋下，或寫不回新副本的修改不再沿用，重試會從目標分支重新修改。
- 重試的基底：只有接續上面那種保留的修改時才沿用原基底。其他重試（目標分支基底驗證失敗、安裝或準備環境失敗、還沒收集到修改就中斷）一律改用目標分支最新的 commit（追加修改則用 PR 目前的 head），任務時間軸的「開始開發」寫出新基底；所以修好目標分支並合併後，直接按重試即可（#261）。
- 預留額度：辨識預留租約為五分鐘、開發為三十五分鐘；中斷的孤兒預留到期後回收，無法確認的費用保守計入預估用量。辨識會依圖片、上下文與輸出上限調整預留，逾時或缺少用量回報也會估算記帳。
- 群組辨識失敗：連續三次後停止辨識、保留原始訊息並通知。排除憑證或服務異常後，在群組頁按「重新辨識」，保留的訊息會重新判讀。判讀停止期間，群組成員用 `/任務` 提出時，「收到」會說明判讀暫停、訊息已保留。
- 群組改綁或重新啟用：從新訊息開始，舊的未執行需求需要重新確認；不會突然處理停用期間的歷史對話。
- PR 建立時取消：已在傳輸中的 GitHub 請求可能完成，系統保留取消狀態，另以稽核紀錄與通知提供該 PR 連結供人工處理。

## 執行隔離

可信服務持有 LINE、OpenAI 與 GitHub App 機密。工作容器僅取得短效執行授權，代理限制模型、用途、版本、時間與剩餘估算額度。工作容器非 root、根目錄唯讀、無主機目錄及 Docker socket，並限制 CPU、記憶體與程序數。

安裝階段只能透過 Squid 代理連線至指定 HTTPS 套件來源；私有網路、主機及其他目的地均拒絕。下載來源白名單在看板「系統 → 下載來源白名單」維護（預設值見 `infra/egress/allowed-domains.txt`），變更寫入稽核。測試階段沒有網路。開發與審查僅連到內部代理網路；審查的工作副本唯讀。原始 Git 基底另外唯讀掛載，差異收集不信任專案可修改的 `.git`。

Codex SDK 在上述隔離容器內使用 `danger-full-access`，避免 Docker 禁止建立巢狀命名空間而使檔案操作失敗；此設定不可直接用於主機執行。安全邊界仍由 Docker 的非 root、唯讀根目錄、移除權能、隔離網路、唯讀審查掛載及限權代理強制執行。

目前工作映像包含 Node.js 24、.NET 8 SDK、Git、Python、編譯工具、Playwright Chromium、`ping`（`iputils-ping`）、`nc`（`netcat-openbsd`），以及完全存取專案用的 OpenSSH 用戶端、`sshpass` 與 `agentflow-ssh`。測試需要 SQL Server 的專案自動改用 `line-agentflow-worker-mssql:local`；其他系統工具可由 AI 提出、經審查後裝成專案衍生映像（見[自動準備專案測試環境](agents/project-environment.md)）。自訂映像要以最新的 `worker/Dockerfile` 為基底，保留 `io.agentflow.worker=v1` 標記、不舊於程式要求的 `io.agentflow.worker-rev` 與 `/opt/agentflow` 工具，並重新驗證專案。私有套件需要另行設計限權下載方式，不能把主機或 GitHub 寫入金鑰傳入工作容器。

## 備份及還原（進階）

一般的備份、搬機流程見 [部署手冊的〈備份、還原與搬機〉](deployment.md#備份還原與搬機)；以下是手動指定資料庫的做法。

手動備份：

```powershell
docker compose exec app npm run backup
```

備份位於正式服務資料卷 `/data/backups`，包含設定、成員名單、專案、群組、任務與記錄；不含原始聊天、圖片、登入工作階段、執行授權或工作容器內容。每份檔案以 AES-256-GCM 加密，保留七個日期。

還原前停止派工，建立空白 PostgreSQL 資料庫並設定 `DATABASE_URL`，準備原本 `.local/secrets.json` 的 `sessionSecret`，然後執行：

```powershell
npm run restore -- C:\備份位置\agentflow-2026-11-04.afbackup
```

還原程式拒絕覆蓋有資料的資料庫；完成後保持全域暫停、群組停用、專案待驗證。原本進行中的任務轉為待人工處理，遠端 Issue／PR 不會自動重建。確認記錄與 GitHub 遠端狀態後，重新驗證環境、配對通知並逐步啟用。

成員名單自備份格式第 3 版起納入。還原更早的備份時，還原程式會提示名單未包含；此時只有擁有者能登入，須到看板重新加入其他管理者與成員。

不要使用 `docker compose down -v` 作為日常停止指令，這會移除資料卷。失敗工作副本可能包含專案機密與衍生資料，保留僅供排錯；系統會在保留期限到期後清理已結束執行的工作資料卷。

## 已知邊界

背景佇列保存外部錯誤時只保留固定格式的 HTTP 狀態或連線逾時／中止原因，不保存供應商原始 request、response、headers、body 或 cause。SDK 將逾時包成 HTTP 500 時，仍辨識有限的逾時原因；完整原始例外不應作為排錯附件。工作名稱、任務時間軸及服務狀態用來確認失敗階段，原有有界重試規則不變。

GitHub 一般 API 與 App 憑證取得請求，每次各有三十秒總期限，涵蓋等待標頭及完整回應本文；逾時會中止連線，不能把半截 JSON 當成成功。API 本文另有 64 MiB 上限，不影響有獨立期限與串流限制的專案封存檔下載。逾時不會讓後續請求沿用已失效的取消訊號。

本機完全離線時不能主動發送故障通知，恢復後才記錄服務心跳中斷。固定 HTTPS 入口（Cloudflare Tunnel、ngrok 或自備程序）的狀態由通道狀態檔 `.local/tunnel-status.json` 與服務錯誤呈現；ngrok 免費配額耗盡等供應商端的問題需由管理者在供應商後台確認；沒有自動購買或升級功能。模型列表可讀取只代表基本帳號權限，實際模型能力、價格與帳號配額仍須在串接驗收時確認。
