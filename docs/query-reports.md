# 查詢報告與補充圖片

對應 Issue #63 與 閱讀體驗改善 #66。

## 閱讀順序

新查詢依問題選擇深度：用途先說能做什麼並給具體例子；欄位題直接比較用途；流程題先說起點與結果；即時狀態缺少證據時，第一句直接說無法確認，不用歷史文件推論現況。開頭重點以 80～180 個中文字為目標，最多三點，簡短事實可只寫一句。簡單用途題全文以約 400～800 字為目標，複雜或明確要求完整調查時才展開；影響結論的限制必須保留在摘要。

只有能幫助理解本題時才加入圖解，預設使用直向流程、三至五個節點，最多七個，避免混合設計者與使用者操作。看板直接顯示短答、例子與圖解；二級標題「詳細資訊」與「程式依據」分別以「展開詳細說明」與「查看程式依據」收合。以 Markdown 語法樹辨識章節，保留跨段引用並忽略程式碼中的標題。舊回答保留原文，符合章節格式時套用收合；沒有開頭內容的報告保持完整顯示。

看板支援標題、清單、表格、程式碼、複製全文，以及圖形縮放、重設和全螢幕。圖形以原始尺寸置中顯示，不強制放大小圖；超出窄螢幕時可橫向捲動。LINE 通知只保留開頭重點，表格改成文字列點，摘要含截短提示最多 320 字元，另附完整任務連結；GitHub 保留完整 Markdown 與 Mermaid，圖片改為登入看板查看。

## 圖片來源與發布

可引用本需求版本的訊息圖片、儲存庫既有圖片或目前權限可存取的真實畫面截圖，不生成假畫面。每份最多三張 PNG、JPEG 或 WebP，每張最多 2 MiB、總計最多 6 MiB。畫面無法存取時，報告說明缺少的證據。

查詢工作將附件放在獨立的 /tmp/agentflow-report 暫存目錄，並以 manifest.json 列出：

    [{"key":"img-1","file":"screen.png","caption":"機台對應結果","kind":"screenshot","source":"https://example.test/machines","capturedAt":"2026-11-10T08:00:00Z"}]

kind 可為 message、repository 或 screenshot。訊息來源使用提供的 sourceId，且必須與該版本提供給模型的圖片位元組相同；專案來源使用相對路徑；截圖來源須提供網址及時間，保存時移除網址帳密、查詢參數與片段。報告以 ![圖說](report:img-1) 引用。

工作程序在退出、清理容器之前收集附件。收集器固定目錄描述符，拒絕越界檔名、符號連結、硬連結與非一般檔案，並限制讀取大小。服務端重新驗證格式、位元組、來源及實際圖片解碼，再於同一交易儲存回答、附件與執行結果；取消或版本更新後的晚到結果不得發布。

query_report_images 綁定任務、執行與需求版本；任務詳情只回傳圖片中繼資料。GET /api/tasks/:id/report-images/:imageId 沿用任務登入規則，檢查來源撤回、保存期限、圖片雜湊及需求版本，回應 Cache-Control: no-store。背景清理移除失效圖片；開啟中的看板每三十秒更新圖片有效性。已經交付到使用者裝置的位元組無法追回，後續存取與顯示依有效性更新。

## 呈現限制

Markdown 不解析原始 HTML；外部圖片不直接載入，只呈現已驗證的報告附件。Mermaid 採嚴格模式，只接受 flowchart/graph，限制八千字、五十條邊及圖形尺寸，不接受內嵌設定或外部資源。以 SVG 圖片呈現，解析失敗時顯示文字說明與可展開的原始內容。

實作依據：[React Markdown 官方文件](https://github.com/remarkjs/react-markdown)、[Mermaid 安全設定](https://mermaid.js.org/config/schema-docs/config-properties-securitylevel.html)。

## 驗證與部署

執行型別檢查、報告與附件測試、完整測試及建置。共用 Docker 主機可指定 ACCEPTANCE_WORKER_IMAGE，先建立新版測試映像，避免驗收提前更換正式映像。

部署時先套用新增資料表與函式，再更新看板、服務、執行器及工作映像；使用中的衍生映像須繼承新版工作程式與版本標記。回退服務時保留新增資料結構，舊回答仍可閱讀。

本輪隔離驗收使用 設備平台 基底 6039cfd5d450f4f61ac02fdc0f5ac2d9ca4767f5、真實訂閱模型及工作容器；GitHub 發布採替身，LINE 僅檢查通知資料，未向群組送出驗收訊息。首次測試遇到舊工作映像與 Docker 網段不足，更新測試映像、清理未使用的舊驗收網路後重跑；不放寬版本或隔離檢查。

### 閱讀體驗複驗（Issue #66）

使用獨立的 verify-readability 環境與真實訂閱模型，重跑三道原始問題。主檔維護使用 H5 專案 4ac6059、機台欄位使用 設備平台 6039cfd、部署狀態使用 AgentFlow 9168d5b 的原始碼封存。封存驗收不提供正式環境登入或部署資料，不能用來宣稱正式部署狀態。

| 問題                        | 最終驗收結果                                                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 主檔維護的功能是什麼        | 先回答基本資料的查找、新增與修改用途，附日常例子；全文由既有回答 5,507 字元縮為 1,055 字元，程式依據獨立收合。 |
| 設備平台 兩個機台欄位的用途 | 直接區分編號配對與補建名稱，提供來源名稱、組合編號、比對與更新的四節點直向圖。                                 |
| 現在部署進度到哪裡          | 第一行說明目前無法確認，摘要只列缺少的即時證據與確認方式，不把歷史待辦當成今日進度。                           |

首輪發現欄位題漏圖、部署摘要混入舊待辦，修正提示詞後重新產生回答。手機實測也發現小圖強制放大造成裁切，已改用原始尺寸。驗證獨立收合、全文複製（含收合內容）、手機窄螢幕與桌面圖解；LINE 僅驗證產生的摘要，沒有向真實群組發送測試訊息。這三題代表實測案例，不保證所有模型回覆都達到固定長度。
