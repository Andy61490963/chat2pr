總耗時包含重新取得 GitHub App 唯讀授權、容器啟動與準備。分項是工具容器內耗時，故不會等於總耗時。物件大小是磁碟新增量，不是網路流量。同版不呼叫 Git fetch，但仍呼叫 GitHub 驗證授權。

相同基底的準備時間相較原正式紀錄快約 **96 倍**，省約 **600.6 秒**；增量更新約快 **30 倍**。這只比較來源準備，不代表整個 Codex 任務縮短同樣倍數。首次仍須下載專案；不同時段的網路與磁碟快取會影響數字，因此不宣稱冷啟動有穩定加速。

原正式執行 `627b03c7-e8c5-4c46-a5c8-3658b17477ff` 的唯讀基底檔案樹，與新快取的同版工作副本皆為 `756a4bc96d22537fb5f35ebedd5522c02f367963`。四份副本均通過原有差異收集器的零變更檢查，範例前端專案 的 README 與 wwwroot 均存在。

## 執行器與隔離驗收

在獨立執行器的 4313 埠透過真實 `HttpRunner.prepareSource` 再準備兩份 範例前端專案 新版副本，分別耗時 6.623 秒及 4.711 秒。缺少 runner 授權回應 401；觀測 API 回傳快取命中、抓取／快照／副本耗時。

第一份副本寫入驗收檔案，既有收集器只回報該檔案；第二份仍零差異。工作容器看不到 `/cache` 與下載憑證。驗收結束移除工作容器與工作 volume，保留專案快取供後續使用。

## 自動檢查

- `npm run typecheck`、`npm test`（20 個檔案、114 項測試）、`npm run build` 通過。
- 真實 Docker 與隔離 Git 遠端：冷啟動、相同 commit、增量物件、指定舊 commit、可執行位元與符號連結、並行 flock、逾時、取消、錯誤 commit 後恢復均通過。
- 拒絕覆寫已存在的任務副本；任務修改不影響快取、唯讀基底及下一份副本。憑證不落地至快取或 Git remote 設定。
- 即使有快取，GitHub 授權失效或取得授權期間需求版本改變，仍禁止派工；正常準備不再呼叫完整封存檔介面。
- 原本以自建封存檔驗收 RAG／Codex 監看的腳本明確使用隔離封存檔介面，不替虛構儲存庫取得正式憑證。

## 部署範圍

無資料庫遷移。合併後先建置 `line-agentflow-source:local`，再一起更新 app 與主機 runner；升級期間應避免正在執行的任務被 runner 啟動清理中斷。快取可獨立移除並重建，回退 app／runner 不需要還原資料庫。
