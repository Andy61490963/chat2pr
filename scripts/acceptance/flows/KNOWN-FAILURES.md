# 全流程驗收的已知產品缺陷

以下為 2026 年 11 月 26 日在隔離環境重現的缺陷。即使命中下表，同一輪若還有其他不變式異常，整案仍列為新失敗並阻擋合併。故障出現後尚未執行的步驟不算通過。

| 影響 | 重現方式 | 實際證據、原因與建議 |
| --- | --- | --- |
| 高：F12 暫時故障耗盡唯一一次重試（#264） | `npm run acceptance:flows -- 12`，在修改階段依序模擬上游 502 與串流中斷 | 等待第二次退避時，任務已失敗，稽核記錄已自動重試一次。`server/execution.ts` 的 `AUTO_RETRIES` 為 1。依 #264 實作有上限的遞增退避，保留預算、版本及次數檢查。 |
| 高：F13 不可恢復錯誤被重試（#264） | `npm run acceptance:flows -- 13`，模擬模型不存在 | 已觀察上游回傳 404，但最後的稽核分類為暫時性問題並記錄自動重試。`infra/subscription-relay/server.mjs` 將不在允許清單的非成功狀態轉為 502。建議經代理與轉送保留安全的永久錯誤類別；不要把原始上游本文、登入或權杖送到群組。第一個分支已失敗，不推論第二個分支通過。 |
| 中：F10 基底失敗摘要遺漏測試名稱（#266） | `npm run acceptance:flows -- 10`，使虛構專案把票數相減而非相加 | 任務正確失敗；看板只有斷言錯誤及基底比較，沒有測試名稱。將同一個失敗 `node:test` 的輸出交給 `server/test-failures.ts` 的 `parseTestFailures`，原始輸出含名稱，解析結果卻是 `null`。建議補上 Node 測試輸出格式，並驗證群組、看板與後續修復任務沿用同一份清單。 |

只有在隔離環境以同一劇本重現，並確認故障位於正式程式時，才登錄為已知失敗。每筆須記下情境編號、中斷步驟、辨識此故障的證據、最小重現方式、原因與建議修法。同一情境在不同步驟失敗仍屬新失敗。

未實作、環境無法啟動、排隊逾時與刻意注入的故障不列入本表，也不豁免合併前驗證。

登錄後同步更新 `known-failures.ts`，填入情境編號、完整步驟、診斷列與追蹤 Issue。固定劇本完全符合時，帳本仍保留失敗紀錄並註明已知缺陷。額外出現資源殘留、通知、憑證或清理異常時，以新失敗處理。真實模型與故障注入不套用此清單。
